# 高品質 2.5D 混合式美術與場景渲染技術規格

> 文件狀態：長期技術目標與增量實作規格；不是已完成架構或驗收報告。
> 決策日期：2026-11-10
> 適用專案：《零界紀元：THE UNWRITTEN WORLD》
> 依據：07_ART_BIBLE.md、08_TECH_SPEC.md、06_JSON_SCHEMA.md、12_SPEC_AUTHORITY_AND_STATUS.md、09_CONTENT_ROADMAP.md

## 1. 目標與邊界

長期目標為**高品質 2.5D 混合式**：以精緻環境插畫、角色與物件素材為畫面主體，透過場景分層、景深、深度排序、前景遮擋、光影與克制的環境動態，建立有空間感的可探索世界。

本規格不要求全面轉成 3D，也不要求立即導入遊戲引擎。現階段保留 HTML、CSS、原生 JavaScript、Canvas 2D、JSON、GitHub Pages 靜態部署及零預算限制。

目前程式是 DOM/CSS 場景搭配 Canvas 2D 視野／遮罩的原型；不可將其描述為完整 2.5D renderer。此規格定義目標架構與實作順序，不代表程式已完成重構。

## 2. 不可破壞的核心原則

1. **模擬與呈現分離。** 移動、碰撞、互動、謎題、角色狀態與存檔不可依賴某個物件是否被繪製。
2. **單一世界座標。** 角色、障礙、互動區、場景物件與相機使用一致世界座標；相機只改變呈現，不改變世界狀態。
3. **外觀不等於碰撞。** 圖片透明邊界、視覺透視與裝飾不能自動成為碰撞形狀；碰撞幾何由資料明確定義。
4. **外觀不等於遮擋。** 需要遮擋的物件應提供獨立遮擋輪廓／深度資料，不可直接以整張圖片矩形作為遮擋體。
5. **完整背景優先，透明分層可選。** 單張完整背景必須能獨立支撐場景；可選前景／中景失敗時要能降級。
6. **增量、可回退。** 先做最小測試切片；不得為抽象化或追求畫面效果全面重寫現有專案。
7. **桌面優先驗收。** 桌面瀏覽器為現階段主要開發與驗收平台；保留手機／平板相容性，不複製遊戲核心。
8. **品質不以降級換取。** 未經實測與明確取捨，不得降低視野、陰影品質、材質細節、模糊品質或輸入反應。

## 3. 目標分層架構

### 3.1 遊戲核心／模擬層
負責輸入狀態、角色世界位置、移動、碰撞、互動條件、謎題狀態、角色數值及存檔。此層不讀取畫面像素，也不依賴 DOM 節點位置作為唯一世界資料。

### 3.2 場景呈現層
負責世界座標到螢幕座標轉換、相機、場景圖層、素材定位、深度排序、前景遮擋與場景合成。第一階段可以保留 DOM/CSS 與 Canvas 混合方式；是否將部分場景物件統一繪製至 Canvas，須以測試切片比較後決定。

### 3.3 光影與動態效果層
獨立管理視野遮罩、陰影、動態光源、霧氣、水面、粒子、天氣及機關動畫。靜態場景快取不得凍結動態效果；動態效果不得預設成碰撞物件。

### 3.4 UI 層
任務、背包、對話、提示與狀態面板繼續由 HTML/CSS 負責，維持可讀性、鍵盤操作與無障礙語意，不將 UI 文字烙進背景圖。

### 3.5 資源生命週期
資產管理需支援載入、快取、錯誤備援與場景離開時的引用清理。避免每幀重複載入圖片、重複配置大型 Canvas 或大量建立短命物件。

## 4. 場景圖層與排序原則

建議的概念順序如下；實際物件可依場景需求省略圖層：

1. 遠景：天空、遠山、遠處遺跡。
2. 背景建築與地形輪廓。
3. 可行走地面與地表材質。
4. 中景環境物件及可互動物件。
5. 角色與需要依位置穿插排序的物件。
6. 前景遮擋：近景牆體、柱體、枝葉或建築邊緣。
7. 光影、霧氣與動態環境效果。
8. HTML/CSS UI。

排序不能只依圖片檔案順序。需要穿插角色前後的物件，應使用穩定的排序錨點／基準線或明確深度值；不同類型物件的排序規則必須一致。投影方式未定前，不鎖定最終排序公式。

視差只用於視覺深度，不可讓地面、碰撞、互動區與角色位置脫節；須提供關閉或低動態替代。

## 5. 角色、物件與幾何資料契約

每個需要進入場景的視覺實體，概念上應分開管理：

- assetId：引用 assets.json 的穩定資產 ID。
- worldPosition：世界座標位置。
- visualAnchor：圖片對齊點；角色預設以腳底接地點作為位置基準。
- renderSize：畫面呈現尺寸，不等於碰撞尺寸。
- depthKey：排序依據；實際 schema 待資料系統階段定案。
- collisionShape：可選的矩形或多邊形碰撞資料。
- occlusionShape：可選的遮擋輪廓，與圖片透明邊界分離。
- interactionArea：可選互動範圍，使用世界座標。
- lightingProfile：可選光影參數或光源關聯。

以上是責任欄位概念，不是要求現在立刻新增正式 JSON 欄位。正式欄位必須先對照 06_JSON_SCHEMA.md，經資料系統設計後再落地。

現有 L 形牆測試已展示多邊形可作為碰撞與視野幾何的基礎；後續應以同一份幾何資料供碰撞、遮擋及陰影使用，避免外觀輪廓與實際阻擋輪廓各自漂移。

## 6. 美術資產與載入規則

- 依 07_ART_BIBLE.md 與 06_JSON_SCHEMA.md 的目錄、ID、格式及來源規則管理資產。
- 建議目錄仍為 assets/art/backgrounds/、characters/、props/、ui/、effects/；音訊依 schema 管理。
- data/assets.json 是資產索引規格，不代表該檔案或資產目錄目前已存在。
- 場景與遊戲資料引用穩定資產 ID，不直接散落硬編碼路徑。
- 圖片載入失敗時提供 CSS／SVG／幾何佔位或明確錯誤，不可讓核心探索流程白屏。
- 完整背景優先；透明前景、中景、效果圖層為可選增益。
- UI、任務文字、互動符號與重要提示不得烙進背景。
- 不要求人工去背、逐張切圖、逐像素修圖或購買付費工具。
- 每項正式素材需記錄來源／提示詞、授權狀態、審核狀態、用途、alt 與備援，依既有美術聖經執行。

## 7. 光影、粒子與天氣

- 靜態陰影／遮擋可快取；角色位置、光源、通路或遮擋狀態改變時，按必要條件使快取失效。
- 動態光源、粒子、霧氣、水面與天氣使用獨立更新生命週期，不可依賴角色移動才更新。
- 粒子與天氣預設只影響呈現；若特定玩法需要影響移動或數值，必須另有明確的遊戲規則資料，不可讓視覺效果暗中改變碰撞。
- 依視窗範圍裁切繪製，避免更新不可見且無互動的效果；粒子可採可重用物件池，並設定合理數量上限。
- 效果需可停用或降級，但不得把降級當成未經量測的預設方案。
- 光源方向、陰影柔化、霧氣濃度及天氣對比需遵守美術聖經的整體光色一致性。

## 8. 效能與相容性驗收

桌面瀏覽器優先，使用相同瀏覽器、視窗尺寸、DPR、場景與操作步驟做比較。至少涵蓋靜止、持續移動、貼牆、L 形凹角、角色前後遮擋、UI 開啟、動態效果開啟等狀態。

觀察載入是否阻塞、畫面是否跳動、角色是否漂移、陰影是否錯位、動態效果是否凍結，以及操作反應是否改變。必要時再使用瀏覽器 Performance／Memory 工具定位瓶頸。遊戲內診斷浮層不能代替完整 profiler，也不能單獨證明 GPU 成本。

手機／平板列為後續相容性驗收；桌面通過不得推定手機通過。高 DPR、窄螢幕、直橫向、瀏覽器工具列及安全區均需另測。

## 9. 分階段實作路線

### M0：現有原型驗收（先完成）
驗收移動、碰撞、相機、矩形／L 形牆體、視野遮罩、陰影、互動及 UI。L 形牆的幾何靜態檢查不等於實際陰影視覺通過。

### M1：渲染架構穩定化
建立最小可重用的場景呈現責任邊界、世界／螢幕座標轉換、錨點、圖層與深度排序、素材載入快取及錯誤備援。先在測試區完成，不擴張第一章內容。

### M2：正式資料系統
依 06_JSON_SCHEMA.md 建立並驗證正式資產索引與場景資料 loader；先確認 schema 欄位、唯一 ID、路徑存在與缺檔備援，再逐步把測試場景資料化。

### M3：第一章美術整合
依 05_SCENE_CATALOG.md 與 07_ART_BIBLE.md 整合潮痕灘、灰鐘台、下層記錄室。每個場景先確保完整背景可用，再按需要加入透明圖層、動態光影與環境效果。

不得因選定長期美術目標而跳過 M0，或把美術資產製作提前當成技術架構完成。

## 10. 第一個技術切片的範圍

第一個渲染切片應只使用測試區既有內容：

- 一張測試背景素材（可先用佔位圖）。
- 一個角色顯示素材，確認腳底錨點。
- 一面矩形牆與現有 L 形牆。
- 一個可排序的前景遮擋物。
- 一個可選的獨立光影／霧氣效果。

驗收順序：素材載入 → 世界座標定位 → 錨點 → 深度排序 → 前景遮擋 → 碰撞／互動不受影響 → 光影一致 → 效能與錯誤備援。

## 11. 待決事項

以下不得在未測試前寫成正式定案：

- 最終採正交俯視、斜俯視或等角投影。
- 場景物件最終由 DOM/CSS 或 Canvas 2D 負責繪製的比例。
- 深度排序的最終公式與例外規則。
- 正式素材解析度、格式、檔案大小與動畫規格門檻。
- 動態光源、陰影及視差的具體參數。
- 是否有特殊場景需要局部 3D；這不是目前必要工作。

## 12. 完成定義

只有在實際測試並記錄證據後，才可將對應項目標記為已驗證。規格文件建立、程式靜態存在、語法檢查、commit 或 Pages workflow 成功，都不能單獨代表畫面視覺與互動驗收完成。

每次實作交付需記錄 commit、變更檔案、靜態檢查、桌面瀏覽器操作步驟與結果、未測項目及回退方式。若沒有可操作瀏覽器，明確標記未實測。
