# 現行玩法決策與原型盤點（2026-10-22）

> 用途：交接、避免規格與程式混淆。本文是目前工作基準；不代表未實作功能已完成。
> 標記：**已確認**＝專案方向已定；**MVP 必做**＝第一個可玩測試區的驗收目標；**建議預設**＝可用來快速製作的方案，仍可在測試後調整；**待決**＝不可當成已批准的規則。

## 一、目前專案盤點（以 `main` 分支檢視）

### 已存在
- `index.html`：標題畫面、潮痕灘佔位場景、單一「調查潮痕標記」按鈕、對話面板。
- `css/main.css`：響應式版面、CSS 佔位場景、按鈕焦點樣式及減少動態效果偏好。
- `js/main.js`：開始探索、打開／關閉對話、返回標題、Escape 關閉對話，以及基本錯誤提示。
- `tests/manual-test-checklist.md`：現有原型的人工驗收清單；所有項目仍須實際測試，不能視為已通過。
- `docs/`：世界觀、故事、角色、玩法、場景、JSON、美術、技術與路線圖等文件。

### 尚未在現有程式中找到
- 玩家角色的持續移動控制。
- 世界座標、碰撞／阻擋、可延伸的場景範圍。
- 跟隨鏡頭、相機邊界與出生點轉場。
- 場景 JSON 的實際載入／驗證與事件狀態系統。
- 可重複使用的互動物件、秘密發現或會改變世界狀態的謎題。
- 本機存檔、線索簿、任務追蹤與正式章節流程的整合。

### 資料與素材狀態
檢視 `main` 根目錄時，看到 `index.html`、`css/`、`js/`、`docs/`、`tests/`；未看到根目錄的 `data/` 或 `assets/`。因此目前應先用低成本幾何／CSS 佔位素材驗證玩法，並在新增資料前確認實際路徑與既有內容，不假定 JSON 或正式美術已存在。

### 本次盤點範圍限制
這是依 GitHub 上可讀取的檔案所做的靜態盤點；沒有在瀏覽器執行遊戲，也沒有完成桌面、手機、平板或 GitHub Pages 實測。故此處只能說「程式中未找到」，不能代替實際運行測試。

## 二、重要遊戲機制決策

### 已確認的方向
1. **視角與移動**：手機／平板優先的瀏覽器遊戲；俯視／等角 2.5D，玩家直接控制單一主角移動。固定背景上的點擊熱點不能取代主要移動方式。
2. **鏡頭與空間**：鏡頭跟隨主角；玩家能探索初始視窗以外的場景。場景可由單一較大區域或相連小區域構成，不承諾大型無縫開放世界。
3. **核心循環**：移動探索 → 觀察環境 → 接近／互動 → 獲得線索或觸發狀態變更 → 發現秘密／開啟路徑 → 繼續探索。
4. **世界狀態謎題**：至少一個謎題必須讓玩家行動改變明確的世界狀態，且有可辨識的成功回饋；只顯示一段文字不算完整謎題。
5. **碰撞與邊界**：障礙必須阻擋角色；角色與鏡頭不得穿出有效活動範圍或露出不合理的空白。
6. **秘密與線索**：重要發現使用穩定 ID 記錄；一次性發現不能重複發獎。客觀證據、來源記載與推測應能區分。
7. **第一個可玩版本**：先完成一個小型測試區、一名角色、出生點、障礙／碰撞、跟隨鏡頭、一個互動物件、一個秘密、一個狀態謎題及清楚回饋。戰鬥、正式美術與大地圖不列入此階段。
8. **技術邊界**：HTML、CSS、原生 JavaScript、JSON；GitHub Pages 靜態部署；零預算；核心玩法不依賴付費 API、遊戲運行時 AI API 或持續連線後端。

### 建議先採用的低成本預設（不是已批准的永久數值）
- **移動輸入**：手機／平板使用虛擬方向控制；桌面用 WASD／方向鍵輔助測試。互動物件另有清楚的互動按鈕。
- **碰撞**：MVP 先用矩形障礙與簡單角色碰撞箱；碰撞資料與美術圖分開。
- **互動距離**：角色進入物件附近的範圍後，顯示互動提示；由玩家明確按下互動按鈕觸發，避免走過物件就誤觸。
- **相機**：先做穩定跟隨與場景邊界限制，再視手感加入平滑跟隨或前方偏移。
- **謎題範例**：找到線索後啟動一個機關，讓封閉通路變成可通行；機關狀態需保存於當前遊戲狀態，並以畫面或文字回饋。
- **渲染**：先用現有 DOM/CSS 或簡單幾何完成玩法驗證，再依效能與遮擋需求決定是否改用 Canvas；不先做大規模重寫。

### 仍待測試／待決，不能自行寫成定案
- 精確採用俯視或等角投影、世界座標轉換方式。
- 移動速度、加速度、慣性、對角線速度、角色碰撞箱。
- 觸控控制的最終外觀與互動輸入細節。
- 相機平滑度、死區、前方偏移、縮放與遮擋排序。
- 區域大小、資產分區載入、動畫、正式美術與最終渲染方式。
- 存檔格式、完整離線行為及跨裝置同步。
- 後續即時策略性戰鬥的規則、敵人 AI、傷害、資源、裝備與成長系統。

## 三、第一章內容與 MVP 的關係

正式故事規劃仍保留第一章場景 ID：
- `ch01_tide_mark` — 潮痕灘
- `ch01_grey_bell` — 灰鐘台
- `ch01_record_room` — 下層記錄室

但**第一個技術測試區不必一次完成這三個完整場景**。先在小區域證明移動、碰撞、鏡頭、互動、秘密與狀態謎題可行，再將通過驗證的系統接回正式章節資料。不得為了玩法測試擅自改動世界觀、故事或角色聖經。

## 四、下一步與驗收順序

1. 以佔位素材實作主角移動及一致的方向控制。
2. 加入碰撞、活動範圍與場景邊界。
3. 加入跟隨鏡頭，確認能看到初始畫面外的區域。
4. 加入觸控控制及可理解的移動／受阻回饋。
5. 加入一個互動物件、一個可發現秘密、一個狀態改變謎題。
6. 在桌面瀏覽器、手機直向／橫向、平板分別驗收；每項記錄裝置、瀏覽器、步驟、預期與實際結果。
7. 通過後再決定最終座標／投影、資料格式細節與正式美術投入。

**狀態原則：** 文件已更新 ≠ 程式已實作；程式已提交 ≠ 功能已通過；桌面測試通過 ≠ 手機／平板或 Pages 部署已驗證。
