## 1. 專案願景

### 1.1 一句話願景

**[已確定]** 《零界紀元：THE UNWRITTEN WORLD》是一款以瀏覽器為平台、以單人探索和敘事為核心的免費遊戲。玩家將走進一個被歷史遺忘、由文明遺跡與未知線索構成的世界，透過觀察場景、互動調查、收集記錄和連結線索，逐步拼出世界曾經發生的事，以及自己在其中的位置。

### 1.2 專案目標

1. 建立有一致規則、歷史層次、文明痕跡與長期謎團的原創世界。
2. 以精緻的 2.5D 場景、分層視差、粒子、霧氣、光影和互動熱點，營造接近立體空間的沉浸感。
3. 讓探索和故事互相支持：場景不只是背景，每個重要地點都應傳遞情緒、歷史或可追查的線索。
4. 讓沒有程式與美術背景、只有手機或平板的專案擁有者，仍能以免費工具和 AI 輔助逐步完成遊戲。
5. 使用 HTML、CSS、原生 JavaScript 與 JSON 建構遊戲，最終可由 GitHub Pages 以靜態網站形式發布。
6. 讓遊戲核心在沒有遊戲運行時 AI API、沒有自建伺服器、沒有付費服務的情況下正常運作。
7. 先完成小而完整、可實際遊玩的垂直切片，再逐步擴展內容，避免只有龐大設定而沒有可玩的成果。

### 1.3 不以什麼作為成功標準

- 不以世界觀文件的長度代替可玩的遊戲。
- 不以生成了多少圖片代替場景品質與一致性。
- 不以程式碼的複雜程度代替穩定性。
- 不把「AI 說已完成」視為驗收；必須有可查看的檔案、實際測試或可重現的檢查結果。
- 不承諾在沒有預算、沒有專職團隊的前提下，一次製作出無限規模的商業級開放世界。

### 1.4 產品邊界

**[已確定]** 第一階段以單人、瀏覽器、靜態網站、探索、互動與劇情為核心。

**[建議採用]** 第一個可玩版本採用「場景節點式探索」：玩家在一個場景中觀察背景、點選互動熱點、閱讀文字、取得線索，再前往相連場景。透過背景層次、細微動態、環境音（若能免費且授權清楚）與過場效果建立空間感，不以真正的 3D 引擎為前提。

**[尚待決定]** 最終總章數、完整地圖規模、主線長度、結局數量、角色配音、是否加入戰鬥或複雜解謎。這些項目不得成為第一個可玩版本的阻塞條件。

## 2. 目標玩家體驗

### 2.1 玩家應感受到什麼

- **好奇**：場景中存在值得觀察、但不會一次說明白的細節。
- **孤寂與尺度感**：遺跡暗示世界遠比玩家眼前所見更古老、更廣大。
- **發現感**：玩家能從不同來源的記錄拼出新的理解，而非只靠角色直接講解。
- **可信的未知**：謎團有線索、有規則、有可能回頭驗證的依據，不是任意反轉。
- **可控的探索**：玩家知道自己可以做什麼、已經發現什麼，以及下一步有哪些合理方向。
- **安靜的沉浸**：介面不應不必要地打斷閱讀；動態效果應服務於氛圍和注意力。

### 2.2 一次遊玩流程的體驗標準

1. 玩家進入遊戲後，能快速理解目前身處何處，以及如何開始。
2. 場景首先以構圖、光線和環境細節吸引玩家，而不是用大量說明文字壓住畫面。
3. 可互動區域能被發現；重要互動不可只依賴極小、難以點中的像素。
4. 玩家點選熱點後，會得到有意義的反應，例如描述、角色回應、線索、物品記錄、狀態變化或場景移動。
5. 新線索能被保留在日誌、資料庫或線索頁面中，避免玩家必須靠記憶才能繼續。
6. 玩家離開或重新整理頁面後，若該版本宣稱支援存檔，進度應能恢復；未支援時必須明確說明。
7. 任何主要流程都不應要求玩家登入、付費、連接外部 AI 服務或建立帳號。

### 2.3 無障礙與手機優先

**[已確定]** 專案擁有者只有手機或平板，因此工作流程和遊戲介面都必須考慮觸控。

**[建議採用]**
- 先以直向與橫向皆可閱讀的響應式設計為原則；場景探索可優先針對橫向螢幕最佳化，但必須提供清楚提示或可用的直向佈局。
- 熱點的實際觸控範圍應比可見圖示更寬裕；避免要求精準點擊細小物件。
- 正文、按鈕、日誌與設定在常見手機尺寸下應可讀，不可被瀏海、瀏覽器工具列或螢幕邊緣遮住。
- 提供文字大小或至少避免固定小字；對比不足時應改善。
- 動畫應節制，並考慮減少動態效果的偏好。
- 不用顏色作為唯一線索提示方式。
- 互動元件需具備清楚的焦點、按下或選取狀態。

**[尚待決定]** 是否需要多語言、螢幕閱讀器的完整無障礙支援與獨立字幕選項。第一版仍須避免明顯的觸控與可讀性障礙。

## 3. 遊戲類型與核心特色

### 3.1 類型定義

- **[已確定]** 單人探索敘事遊戲。
- **[已確定]** 瀏覽器執行，核心技術為 HTML、CSS、原生 JavaScript、JSON。
- **[建議採用]** 以 2.5D 場景呈現、節點式移動、點擊互動、環境敘事、線索收集和劇情解鎖為主要形式。
- **[尚待決定]** 是否加入角色養成、物品合成、戰鬥、數值成長、隨機生成或多周目系統。沒有必要時不應為了「像大型遊戲」而加入。

### 3.2 核心特色

1. **可探索的文明遺跡**：建築、工具、壁畫、機械與地景都能反映曾經存在的文明。
2. **多層歷史**：不同時代留下的證據可能互相矛盾；玩家需要比較來源與背景。
3. **環境敘事**：用場景位置、物件狀態、破壞痕跡、光線和空間關係傳達故事。
4. **可追蹤的謎團**：重要問題應有線索清單、已知事實與尚未解答部分。
5. **2.5D 沉浸呈現**：靜態或近靜態背景配合多層視差、粒子、霧氣、微光、光影與細微動態。
6. **低門檻互動**：點擊、閱讀、選擇、調查和切換場景優先於複雜操作。
7. **離線可執行的核心邏輯**：遊戲內容與規則在建置時準備好，不在遊戲執行時呼叫生成式 AI。

### 3.3 核心遊戲循環

**抵達場景 → 觀察環境 → 發現熱點 → 調查／閱讀 → 取得線索或改變狀態 → 更新日誌／線索簿 → 解鎖路徑或新理解 → 前往下一個場景 → 回頭重新理解先前線索。**

每個主要場景至少應具備：
- 一個明確的場景目的或情緒主題。
- 一個值得觀察的視覺焦點。
- 至少一個有效互動（若該場景是純過場，需明確標示其用途）。
- 一項可傳遞的資訊：世界觀、角色、歷史、謎團或方向提示。
- 合理的進入與離開方式。
- 在內容設計允許的情況下，至少一項可記錄或可回顧的發現。

### 3.4 第一個可玩版本的預設範圍

**[建議採用]** 第一個垂直切片（Vertical Slice）只做一段短而完整的體驗，建議包含：
- 3 個彼此連接的場景；
- 1 個主要探索區域；
- 6–10 個有意義的互動熱點；
- 1 個可追查的核心謎團；
- 1 本簡單的探索日誌或線索簿；
- 至少 1 次由玩家行動觸發的場景或故事狀態變化；
- 清楚的開始、過程與暫時性結尾；
- 手機和平板上的基本操作測試。

這是規劃建議，不代表內容已製作。若免費生成或人工整理的素材不足，應縮小場景規模而非降低檔案授權與穩定性要求。

## 4. 核心遊戲系統原則

### 4.1 場景系統

**[建議採用]** 每個場景以 JSON 描述識別碼、標題、背景資源、可互動熱點、敘事文字、連接場景與可見條件。JavaScript 負責載入資料、顯示場景和處理互動；不把大量故事文字硬寫進核心程式。

場景資料至少應能表達：
- 唯一且穩定的場景 ID；
- 玩家可讀的名稱與描述；
- 背景圖及可選的前景／中景／遠景圖層；
- 熱點的 ID、顯示區域、互動文字與互動結果；
- 進入條件、顯示條件或解鎖條件（若有）；
- 可前往的場景 ID；
- 相關日誌或線索 ID；
- 素材授權或來源紀錄的參照（由資產清單管理）。

具體 JSON 欄位由 `06_JSON_SCHEMA.md` 定義。若該文件尚未完成，AI 不得各自發明互不相容的欄位格式。

### 4.2 互動與狀態

**[建議採用]**
- 互動結果以明確的資料和狀態變化描述，例如「已讀取記錄」「已取得線索」「門已解鎖」。
- 同一熱點重複點擊時，結果應可預期；不可無意間重複發放關鍵物品或讓劇情倒退。
- 鎖定的互動應說明目前缺少什麼，或提供可理解的提示。
- 不用只有開發者看得懂的錯誤訊息面對玩家。
- 對關鍵狀態使用穩定 ID，不以畫面文字作為程式判斷的唯一依據。

### 4.3 存檔

**[建議採用]** 第一個可玩版本使用瀏覽器的 `localStorage` 保存少量本機進度，例如已訪問場景、已取得線索和設定。此存檔僅存在於目前瀏覽器／裝置，清除網站資料、使用無痕模式或更換裝置可能會遺失。

- 存檔讀取必須能處理空資料、損壞資料與版本差異。
- 提供「重新開始」或清除存檔功能前，應有明確確認。
- 不上傳玩家資料，不建立帳號，不宣稱雲端同步。
- 若存檔尚未實作，介面與文件不得宣稱具備存檔。
- **[後續可選]** 手動匯出／匯入存檔；不得成為第一章核心通關或基本存檔驗收的必要條件。

### 4.4 日誌與線索簿

**[建議採用]** 將玩家已發現的內容整理為可回顧的記錄，至少區分「已確認的發現」與「玩家／敘事者的推測」。不要把尚未證實的角色猜測寫成世界觀事實。

### 4.5 失敗與錯誤處理

- 缺少背景圖時，顯示可辨識的佔位畫面或替代背景，不讓整個介面消失。
- 某一筆 JSON 格式錯誤時，應盡可能顯示有用的錯誤資訊，並在開發模式協助定位檔案。
- 無效的場景連結應被測試工具發現。
- 所有按鈕與熱點都必須有實際效果；不可留下看似可按、實際沒有功能的裝飾性控制。
- 網頁刷新、視窗尺寸改變或連續點擊，不應讓核心流程進入無法恢復的狀態。

## 5. 世界觀設計原則

### 5.1 世界觀的敘事方向

**[已確定]** 世界需要具有廣大的歷史縱深、未知歷史、文明遺跡、探索感、謎團與多層劇情。

**[建議採用]** 以「可追查的證據」而不是「一次說完的百科全書」來呈現世界。玩家先看見痕跡，再逐步推導原因；新資訊可以改變舊資訊的解釋，但不應任意推翻已建立的規則。

### 5.2 世界觀的事實層級

所有世界觀資料應標明以下層級之一：

1. **客觀已確立事實**：由專案主設定明確確認，其他文件不得自行改寫。
2. **可靠來源的記錄**：角色、碑文、檔案或遺物所記載的內容；記錄本身可能有偏差。
3. **角色／文明的信念**：某個群體相信的事情，不保證是真相。
4. **待驗證假說**：有部分線索支持，但尚未定案。
5. **刻意保留的謎團**：作者知道或尚未決定答案，玩家暫時無法確認。
6. **開發備註**：只供製作團隊使用，不應不小心出現在遊戲對白中。

### 5.3 建立與管理謎團

每個主要謎團應記錄：
- 謎團 ID 與核心問題；
- 玩家第一次接觸它的場景；
- 已出現的線索及其來源；
- 目前能支持哪些解釋；
- 哪些解釋已被證據排除；
- 預計在哪個階段揭露部分答案；
- 最終答案狀態：已定案、刻意保留或尚待決定；
- 可能造成的劇情連鎖影響。

AI 不得只為了驚訝感加入沒有鋪墊的新設定。重大反轉必須能回頭找到至少一項先前線索，或清楚解釋為何原有證據被誤讀。

### 5.4 文明與遺跡

- 每個重要文明都應有可辨識的生活方式、技術能力、資源限制、價值觀和留下的痕跡。
- 不同文明不能只靠換一套名稱或顏色區分。
- 遺跡的建築、物件、文字、磨損與毀壞方式應符合該文明的材料與技術條件。
- 遺跡必須服務於探索、情緒或敘事，不只是無意義的裝飾。
- 重要歷史事件要記錄大致時間、參與者、原因、結果及證據來源；日期系統尚未定案前，不得擅自建立互相矛盾的時間線。

### 5.5 劇情一致性管理

**[建議採用]** 以 `01_WORLD_BIBLE.md` 管理世界規則與歷史，以 `02_STORY_BIBLE.md` 管理主線、章節和劇情揭露，以 `04_CHARACTER_BIBLE.md` 管理角色，以 `05_SCENE_CATALOG.md` 管理場景與互動。若文件內容衝突，先標記衝突、指出受影響項目，再提出最小修正方案；不得默默選擇其中一個版本並覆蓋其他設定。

**[尚待決定]** 世界的終極真相、主要角色完整名單、主要文明名稱、歷史紀年、主線結局與玩家角色背景。可以提出候選案，但只有明確批准或正式寫入相應設定文件後，才算定案。

## 6. 美術風格方向

### 6.1 整體視覺方向

**[已確定]** 以精緻的 2.5D 場景為主要視覺形式，運用 AI 生成背景、分層視差、粒子、霧氣、光影、互動熱點與場景轉換，創造近似立體的探索體驗。

**[建議採用]** 方向為「電影感的科幻奇幻遺跡」：大尺度環境、清楚的視覺焦點、具有年代感的建築與物件、有限而有目的的色彩配置、空氣透視與克制的發光元素。這是方向，不是已完成的美術定稿。

### 6.2 2.5D 場景的製作原則

- 先生成／取得一張完整構圖的背景作為可用基礎，再視需要拆成遠景、中景、前景、霧層或光效層。
- 只有在能增加深度或氛圍時才增加圖層；不要求每張背景都拆成大量圖層。
- 視差幅度應小而穩定，避免大幅移動造成暈眩、穿幫或不自然的透視。
- 粒子與霧氣應以 CSS 或 Canvas 等原生技術實現，並限制數量和更新成本。
- 光影效果必須在中低階手機上保持流暢；可以使用漸層、透明圖層與簡單動畫代替昂貴的即時效果。
- 重要互動物件的視覺位置需與熱點位置一致。
- 場景在不同螢幕比例下要保護主要焦點，避免重要建築、角色或熱點被裁掉。

### 6.3 美術一致性

每個正式場景都應遵守統一的場景規格，至少記錄：
- 場景 ID、敘事目的與情緒關鍵字；
- 構圖焦點、視角高度和鏡頭方向；
- 時段、天氣、主要光源與主色調；
- 建築材料、年代感、科技程度和環境細節；
- 圖層拆分方式及預期動態；
- 重要物件的位置和互動熱點；
- 圖片來源、生成方式、授權／使用條款檢查狀態；
- 圖片尺寸、檔案格式和壓縮狀態。

AI 生成的圖片可能在建築細節、透視、標誌和物件位置上出現錯誤。不可直接假設生成圖每個細節都符合設定。優先選用無文字、可作為場景背景的構圖；必要文字、符號與 UI 由 HTML/CSS 呈現，避免將重要文字直接烙在生成圖內。

### 6.4 角色與物件

**[建議採用]** 第一版優先採用環境敘事、檔案、雕像、遺物、遠景剪影或有限角色肖像，避免一開始就依賴大量一致的全身角色動畫。角色外觀如需多張圖，應先建立文字設定與參考圖規範，降低 AI 多次生成的差異。

### 6.5 素材驗收

- 圖片在手機上放大查看時，沒有嚴重破圖、明顯生成瑕疵或不符合世界觀的現代物件。
- 重要畫面沒有不應出現的文字、水印、商標或未授權角色。
- 圖片檔案大小符合行動裝置載入目標。
- 圖片不應以資料 URI 或巨大內嵌字串塞進 JSON；使用有意義的檔案路徑。
- 若圖片來源或授權不明，先隔離，不得當作正式發布素材。

## 7. 技術架構原則

### 7.1 技術基線

**[已確定]**
- HTML：頁面結構。
- CSS：版面、響應式設計、視差、粒子與簡單動畫。
- 原生 JavaScript：場景切換、互動、狀態管理、資料載入與存檔。
- JSON：場景、對話、線索、物件與其他內容資料。
- GitHub Pages：靜態網站發布。
- 不依賴遊戲運行時的 AI API 或伺服器。

### 7.2 建議的簡單目錄結構

**正式目錄決策：** GitHub Pages 使用 `main` 分支的 `/(root)`。網站入口與遊戲檔案放在 repository 根目錄及其子目錄；`docs/` 只保存規格、交接與驗收文件。實際檔案可分階段建立，不代表目前已存在：

- `index.html`：遊戲入口。
- `css/`：樣式檔。
- `js/`：遊戲程式。
- `data/`：JSON 內容資料。
- `assets/art/`：背景、圖層、角色、道具與 UI 圖片；完整子路徑以 `data/assets.json` 為準。
- `assets/audio/`：經確認授權的音效或音樂（若有）。
- `docs/`：設計、規格、工作流程與驗收文件。

這是建議結構，不代表目前所有資料夾或程式已建立。Git 不會保留空資料夾；需要時應建立帶有實際檔案的目錄。

### 7.3 架構分層

1. **呈現層**：負責畫面、版面、熱點和動畫。
2. **遊戲邏輯層**：負責場景切換、條件判斷、互動結果和進度狀態。
3. **內容資料層**：JSON 儲存場景、敘事、線索與互動定義。
4. **資產層**：本地或專案內的圖片、音效和其他靜態資源。
5. **持久化層**：必要時用 `localStorage` 儲存本機進度與設定。

各層應保持清楚邊界。新增場景或對話時，優先新增／修改資料，而不是複製整段核心程式。不得為了小功能引入大型框架或複雜建置流程，除非有清楚的必要性與免費可行的替代方案比較。

### 7.4 GitHub Pages 相容性

- 網站必須可作為靜態網站發布；不能依賴 Node.js 伺服器在玩家端執行。
- Pages 發布來源固定為 `main` 分支的 `/(root)`；網站入口預定為根目錄 `index.html`，遊戲檔案位於 `css/`、`js/`、`data/`、`assets/`，規格文件僅放 `docs/`。
- 使用以網站根目錄為基準的路徑時，必須由單一基底路徑工具處理 repository 子路徑；不可硬寫網域根路徑。
- 檔名大小寫必須一致；本機可能看似可用的大小寫錯誤，在發布環境可能失敗。
- 不將秘密金鑰、私人憑證或 API 金鑰放入公開儲存庫。
- 資料檔與圖片應能從發布網址正常載入；不依賴本機檔案系統路徑。
- 不以 `file://` 開啟網頁作為唯一測試方式，因瀏覽器的本機檔案限制可能影響 JSON 載入；應在 GitHub Pages 或適當的靜態預覽環境測試。
- 任何新增外部套件都要評估免費性、授權、維護狀態、手機操作難度和是否能移除。

### 7.5 效能與穩定性

**[建議採用]**
- 先讓低效能裝置可以完整遊玩，再逐步增加效果。
- 優先使用 CSS 透明度、變形與漸層等簡單效果；避免每一幀都進行大量 DOM 變更。
- 限制同時運作的粒子數、動畫層和高解析度圖片。
- 大圖在合理範圍內壓縮，優先採用瀏覽器支援良好的格式；需要時提供相容的替代格式。
- 避免在每次點擊時重複載入相同資產。
- 在必要時提供「減少效果」或低動態模式。
- 不把載入速度、FPS 或相容性宣稱為已達標，除非實際測試並記錄。

### 7.6 安全與隱私

- 第一版不收集玩家個人資料，不需要登入。
- 不加入追蹤器、廣告 SDK 或未經明確必要性評估的第三方分析工具。
- 不執行從不可信來源下載的程式碼。
- 外部連結若有必要，應清楚標示；核心遊戲不可因外部服務停用而無法進行。
- 遊戲不需要 API 金鑰；若 AI 協作工具使用了帳戶連線，那是開發階段工作流程，不得把該憑證放進遊戲程式或公開檔案。

## 8. 免費工具與資源限制

### 8.1 硬性成本規則

**[已確定]**
- 專案預算為零。
- 不購買美術、音樂、字型、外掛、範本或其他素材。
- 不使用付費 API。
- 不把付費方案、試用期結束後收費或必須付費才能匯出的功能，設計成必要工作流程。
- 遊戲運行時不呼叫 AI 生成服務。
- 以免費可使用的工具與素材為優先；但「可以免費下載」不等於「允許任何用途」。

### 8.2 工具選用原則

**[建議採用]**
- GitHub 網頁介面：管理檔案、提交修改和發布專案。
- GitHub Pages：靜態網站託管，依 GitHub 當前條款與使用限制使用。
- 免費 AI 介面：用於草擬、程式生成、劇情整理、除錯與美術提示詞；使用前確認當前免費額度和條款，不假設額度永久存在。
- 免費圖片處理工具：只在確實需要裁切、縮放、壓縮或轉檔時使用；應可在手機／平板瀏覽器操作。
- 免費音效／音樂來源：只有在授權允許遊戲使用、修改（如需要）及公開發布，且能記錄作者與條款時才採用。
- 原生瀏覽器技術：優先減少外部依賴。

工具名稱、免費額度與服務政策可能變動。AI 推薦工具時應先確認目前可用性；不能確認時標記「需核實」，不可宣稱永久免費。

### 8.3 素材授權與來源管理

每項外部素材至少記錄：
- 素材 ID、檔名與用途；
- 原始來源 URL；
- 作者或發布者（若有）；
- 授權名稱與相關限制；
- 是否允許商業使用（即使目前不以商業化為目標也應記錄）；
- 是否要求署名、附帶授權文字或公開修改版本；
- 下載／確認日期；
- 核查狀態與核查者。

AI 生成素材也應記錄使用工具、生成日期及相關服務條款的檢查結果。不得把 AI 生成等同於必然沒有著作權或商標風險。不要要求複製仍受著作權保護的特定作品、角色或藝術家的精確風格。

### 8.4 資源不足時的降級順序

若免費 AI 額度用完、生成服務不可用或素材處理太困難，依序採取：
1. 減少場景數量或圖層數量。
2. 重用已授權且風格一致的既有背景，透過不同裁切、光效或互動設計創造變化。
3. 使用 CSS 漸層、簡單幾何形狀和純文字佔位，先完成互動流程。
4. 暫時移除非必要音效、粒子或複雜動畫。
5. 延後不影響核心玩法的內容。

不得以付費素材、付費 API、違規下載或未確認授權的圖片作為補救方案。

## 9. 主要風險與解決方案

| 風險 | 影響 | 預防與處理 |
|---|---|---|
| 專案規模無限膨脹 | 長期只有設定，沒有可玩版本 | 先完成 3 場景垂直切片；每次只擴充可驗收的範圍 |
| 手機操作不便 | 擁有者無法有效管理檔案與測試 | 優先使用 GitHub 網頁介面；提供逐步、可複製的指令或完整檔案，不要求本機終端機 |
| AI 生成程式彼此不相容 | 頁面故障、資料格式衝突 | 先固定目錄、資料契約與 JSON Schema；每次修改需列出變更檔案和測試方式 |
| AI 捏造或改寫世界觀 | 劇情矛盾、設定失去可信度 | 以本文件與設定聖經為準；未定案內容明確標示，不得自行升級成事實 |
| 美術風格不一致 | 世界缺乏整體感 | 先建立美術規範和少量代表場景；生成前重用同一組風格描述與構圖規則 |
| 素材授權不明 | 發布或日後使用風險 | 建立資產清單；來源／授權不明的素材不得進正式版本 |
| 免費工具額度或政策變動 | 工作流程中斷 | 保留可替代工具；內容與程式不依賴特定 AI 服務執行 |
| 圖片過大、效果過多 | 手機載入慢、操作卡頓 | 壓縮圖片、限制圖層與粒子、提供低動態模式、用真實裝置測試 |
| GitHub Pages 路徑錯誤 | 發布後圖片或 JSON 失效 | 使用適當相對路徑，測試實際發布網址與子路徑 |
| 存檔遺失 | 玩家進度受損 | 明確說明本機存檔限制；加入資料版本檢查和錯誤復原策略 |
| 功能看似存在卻無效 | 玩家卡關、驗收失真 | 每個按鈕和熱點都必須實測；無功能的控制不得冒充完成 |
| 需求變更導致返工 | 文件、程式、資料互相矛盾 | 先更新相關規格，再更新實作；重要變更記錄原因與受影響文件 |
| AI 或外部網站不可用 | 進度停滯 | 保持可離線工作的內容與本地靜態遊戲架構；外部服務只用於開發輔助 |

### 9.1 風險處理原則

發現問題時，AI 必須：
1. 說明可觀察到的問題與影響，不誇大、不隱瞞。
2. 區分已確認的原因與推測原因。
3. 提供最簡單、免費且適合手機操作的修復方案。
4. 指明需要新增或修改的檔案。
5. 提供可由非程式設計者執行的驗證步驟。
6. 若無法驗證，標示「尚未驗證」，不得聲稱修復成功。

## 10. 開發階段規劃

每個階段都要有可檢查的產出和通過條件。時間估算不作為硬性承諾；進度以可驗收成果為準。

### Phase 0 — 專案基準與文件治理

**目標：** 確立共用規則，讓不同 AI 不會各自發明互不相容的架構。

產出：
- 本文件 `00_PROJECT_MASTER.md`；
- 世界觀、劇情、玩法、角色、場景、JSON、藝術、技術、內容路線圖與 AI 交接文件的基本架構；
- 明確的已確定／建議採用／尚待決定標記規則。

通過條件：
- 所有文件可在 GitHub 檢視；
- 文件之間沒有明顯互相衝突的硬性要求；
- 後續 AI 知道要先讀哪些文件，以及如何標記未定案內容。

### Phase 1 — 最小玩法與技術原型

**目標：** 先驗證手機瀏覽器能否跑起基本探索流程。

產出：
- 可開啟的遊戲入口頁；
- 至少 1 個測試場景；
- 至少 1 個可點擊熱點；
- 至少 1 次互動回應或狀態變更；
- 基本的場景切換或返回操作；
- 一份手動測試清單。

通過條件：
- 在實際 GitHub Pages 網址可載入；
- 手機／平板可閱讀、可點擊；
- 沒有必須付費或連接遊戲運行時 AI API 的步驟；
- 核心互動有實際效果。

### Phase 2 — 世界觀與垂直切片規劃

**目標：** 讓世界觀、故事與可玩的內容同步設計。

產出：
- 初版世界規則與歷史骨架；
- 第一段故事的開場、目標、線索與暫時性結尾；
- 3 個相連場景的場景規格；
- 第一批互動熱點與線索；
- 第一版 JSON Schema；
- 第一版美術方向與資產清單。

通過條件：
- 每個重要設定有狀態標記；
- 謎團有可追查的線索，不只是一句宣傳描述；
- 場景資料格式一致；
- 素材來源與授權可追溯。

### Phase 3 — 2.5D 視覺與互動整合

**目標：** 把垂直切片從可用原型提升為有氣氛的體驗。

產出：
- 場景背景與必要圖層；
- 視差、霧氣、粒子或光影等經挑選的效果；
- 互動熱點與敘事文字；
- 場景轉換；
- 日誌／線索簿；
- 必要的錯誤與載入狀態。

通過條件：
- 所有核心熱點都能使用；
- 視覺效果不妨礙文字閱讀與點擊；
- 手機上沒有嚴重卡頓或重要內容裁切；
- 失敗時能以清楚方式呈現，而非整頁空白。

### Phase 4 — 進度保存、相容性與品質測試

**目標：** 確保遊戲可反覆使用，而不只是一次性的展示頁。

產出：
- 若採用存檔，完成本機存檔與重置流程；
- JSON 與資產路徑檢查；
- 無效場景連結檢查；
- 手機／平板版面測試；
- 主要流程回歸測試；
- 已知問題清單。

通過條件：
- 重新整理後的行為符合規格；
- 無效資料有可理解的錯誤處理；
- 核心流程可從開始走到暫時性結尾；
- 未解決問題被明確記錄，沒有假裝不存在。

### Phase 5 — 第一個可發布版本

**目標：** 發布一段完整、範圍有限且穩定的遊戲體驗。

產出：
- 可由 GitHub Pages 開啟的版本；
- 清楚的開始方式和操作說明；
- 資產來源／授權紀錄；
- 版本變更摘要；
- 已知限制與下一步計畫。

通過條件：
- 公開網址可從未登入的瀏覽器開啟；
- 所有核心功能經實際測試；
- 沒有必須付費或連線至 AI API 才能玩的功能；
- 沒有已知的重大阻塞錯誤；
- 發布內容與文件的完成狀態一致。

### Phase 6 — 逐步擴展

**目標：** 在每次擴充都可驗收的前提下增加世界、場景、角色與劇情。

每次擴充應遵循：
1. 先更新相關規格和內容清單。
2. 明確列出新增內容與驗收條件。
3. 生成或製作必要資產並記錄授權。
4. 實作內容與互動。
5. 測試新內容及受影響的舊流程。
6. 更新文件、版本摘要與已知問題。
7. 通過驗收後再進行下一批。

不以固定場景數作為永久上限，但每次新增都必須考慮檔案大小、手機效能、內容一致性和維護成本。

## 11. 完成條件與驗收標準

### 11.1 專案階段驗收

一項工作只有在下列條件都符合時，才可標示為「已完成」：
- 交付物已存在於指定的 GitHub 路徑或有可檢視的連結；
- 實際內容符合需求，不只是空檔案、標題或待辦清單；
- 重要功能有實際測試結果；
- 測試環境、測試步驟與已知限制有記錄；
- 沒有把未完成的功能描述成已完成；
- 相關文件已同步更新。

若只完成部分，使用「部分完成」並列出剩餘項目。若只寫出設計稿但尚未實作，應標示「規格完成／尚未實作」。

### 11.2 第一個可玩版本的驗收清單
