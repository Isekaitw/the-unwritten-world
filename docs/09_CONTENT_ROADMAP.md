# 《零界紀元：THE UNWRITTEN WORLD》內容製作路線圖

> 文件代號：09_CONTENT_ROADMAP  
> 文件狀態：正式製作規劃基準 v1.0  
> 適用範圍：專案管理、免費 AI 協作、程式與內容製作、測試及發布  
> 專案平台：手機／平板優先；HTML、CSS、原生 JavaScript、JSON；GitHub Pages  
> 製作原則：先驗證最小可玩流程，再擴充引擎與內容；先用佔位素材驗證技術，不在核心引擎通過前大量生成正式美術。  
> 重要聲明：本文件只規劃後續工作，不代表本次已建立遊戲程式、素材、音效、測試結果或已發布網站。

## 1. 路線圖目的與執行規則

本文件將遊戲製作拆成可以分次交給免費 AI 工具完成的小任務。使用者以手機或平板為主要工作設備，沒有程式設計、修圖或製作預算；因此每個任務都必須產生可檢查的檔案、明確驗收條件，以及失敗時可回退的處理方式。

### 1.1 主要原則

1. **本階段只完成規劃。** 路線圖經確認後，才開始下一階段的第一個可玩原型；不可把規劃文件當作遊戲已完成的證據。
2. **一次只執行一個任務。** 完成後先檢查產出、驗收並提交 Git，再開始依賴它的下一項工作。
3. **核心引擎驗證前只使用佔位素材。** 例如純色背景、簡單 SVG、文字按鈕與短暫靜音；不要先大量生成高解析度場景、角色立繪或特效。
4. **先讓一條流程完整跑通。** 由首頁進入場景、點擊互動、讀取對話、取得道具／記錄、切換場景、存檔及讀檔，再逐步增加內容。
5. **AI 產出必須可審核。** 要求 AI 說明修改檔案、相對路徑、測試步驟、已知限制；不要只接受「已完成」的口頭宣告。
6. **不引入不必要的依賴。** 預設只使用 HTML、CSS、原生 JavaScript 和 JSON；不要求付費服務、建置工具、後端或遊戲運行時 AI API。
7. **每個里程碑都要能回退。** 以小型 Git commit 保存已驗收狀態。若新功能造成既有流程故障，先回到最後一個通過的 commit。
8. **授權與隱私需人工確認。** 不使用來源不明、授權不清的圖片或音樂；不要把密碼、權杖、私人資料放進 repository。

### 1.2 文件依據

執行每項任務前，先讀取與任務相關的正式文件，並以其內容為準：

- `docs/00_PROJECT_MASTER.md`：最高層方向、平台及專案限制。
- `docs/01_WORLD_BIBLE.md`：世界規則、歷史、地區、勢力與謎團。
- `docs/02_STORY_BIBLE.md`：章節劇情與敘事節奏（執行前確認檔案內容與狀態）。
- `docs/03_GAMEPLAY_SPEC.md`：玩家流程、互動和玩法。
- `docs/04_CHARACTER_BIBLE.md`：角色設定、外觀與角色一致性（執行前確認檔案內容與狀態）。
- `docs/05_SCENE_CATALOG.md`：場景 ID、場景順序與第一章場景。
- `docs/06_JSON_SCHEMA.md`：JSON 欄位、資料型別、ID 與引用規則。
- `docs/07_ART_BIBLE.md`：視覺風格、圖片規格、命名與提示詞。
- `docs/08_TECH_SPEC.md`：技術架構、路徑、存檔、錯誤處理、效能與測試原則。
- `docs/10_AI_HANDOFF.md`：AI 協作交接規則（執行前確認檔案內容與狀態）。

若引用文件不存在、內容空白、互相矛盾或不足以決策，先提出差異清單並請專案負責人確認；不可自行編造既定設定，也不可默默覆寫其他文件的正式決策。

### 1.3 里程碑與依賴順序

| 階段 | 任務 | 完成條件 |
|---|---|---|
| M0 規劃與準備 | R00 | 文件狀態、工作範圍及第一個原型驗收條件已確認；尚不製作遊戲 |
| M1 最小可玩原型 | P01 | 能在手機瀏覽器打開，完成首頁至單一佔位場景的基本互動 |
| M2 核心引擎 | E01 | 場景、熱點、對話、事件和資料載入有清楚邊界，錯誤可被看見 |
| M3 第一章內容 | C01、C02 | 三個場景串接；角色、劇情、道具及記錄以資料驅動 |
| M4 存檔與體驗 | S01、U01、A01 | 存讀檔、手機介面與可選音效通過測試 |
| M5 發布與品質 | D01、T01 | GitHub Pages 子路徑可用，關鍵流程測試通過 |
| M6 後續擴充 | X01 | 依已驗證的資料契約擴充章節，不破壞既有存檔與流程 |

**依賴關係：** R00 → P01 → E01 → C01 → C02；E01 也必須先於 S01、U01、A01。D01 可在 P01 後做一次早期部署驗證，但正式發布驗收需等待 C01、C02、S01、U01、A01 的必要部分完成。T01 需在每個里程碑持續執行，並於正式發布前完成完整回歸。X01 只能在第一章穩定後開始。

## 2. 任務清單

## R00 — 規劃基準與文件就緒檢查

- **階段：** M0 規劃與準備
- **目標：** 確認現有設計文件可供製作使用，鎖定第一個原型的最小範圍、任務依賴與驗收方式。本任務只檢查和規劃，不製作遊戲。
- **前置條件：** 已有 repository 與 `docs/` 文件目錄。
- **輸入文件：** `00_PROJECT_MASTER.md`、`01_WORLD_BIBLE.md`、`02_STORY_BIBLE.md`、`03_GAMEPLAY_SPEC.md`、`04_CHARACTER_BIBLE.md`、`05_SCENE_CATALOG.md`、`06_JSON_SCHEMA.md`、`07_ART_BIBLE.md`、`08_TECH_SPEC.md`、`10_AI_HANDOFF.md`。
- **預期產出檔案：** 本文件 `docs/09_CONTENT_ROADMAP.md`；若發現缺漏，另列出待確認清單，未經批准不得直接修改正式設定文件。
- **可直接交給 AI 的任務描述：**

  > 請逐一檢查《零界紀元》列出的正式文件是否存在、是否有實際內容、是否互相一致。這是規劃與文件審查任務，不要建立或修改任何遊戲程式、正式美術、音效或遊戲資料。請輸出文件就緒表、矛盾／缺漏清單、第一個可玩原型的最小範圍、任務依賴順序及驗收檢查表。只陳述你實際讀到的內容；不得把規劃當成已實作或已測試。

- **驗收標準：**
  - 文件清單逐一標示「存在且有內容／存在但空白／不存在／待人工確認」。
  - 第一個原型範圍限定為單一佔位場景與最小互動，不含正式美術和完整第一章。
  - 所有未解決的設定矛盾有明確記錄，沒有擅自替專案作決定。
  - 已確認下一項只執行 P01。
- **可能的失敗情況：** AI 只根據文件名稱猜內容；漏掉空白文件；把設計描述當成已完成程式；不同文件中的命名或路徑不一致。
- **失敗時的處理方式：** 要求 AI 提供每個判斷所依據的檔案與章節；由負責人直接開啟 GitHub 檔案核對。先修正文件或記錄決策，再開始 P01。

## P01 — 第一個可玩原型（佔位版）

- **階段：** M1 最小可玩原型
- **目標：** 建立最小可執行遊戲頁面，驗證 repository、GitHub Pages 路徑和手機瀏覽器能否跑通基本流程。
- **前置條件：** R00 通過；網站目錄規則固定為 `main` 分支 `/(root)`，`docs/` 只保存規格文件。
- **輸入文件：** `00_PROJECT_MASTER.md`、`03_GAMEPLAY_SPEC.md`、`08_TECH_SPEC.md`、`09_CONTENT_ROADMAP.md`)。
- **預期產出檔案：** 最小必要的根目錄 `index.html`、`css/main.css`、`js/main.js`（或依技術規格核准的等效簡化結構）；不建立大量內容 JSON 或正式圖片。
- **可直接交給 AI 的任務描述：**

  > 請為《零界紀元》建立第一個可玩原型，只使用 HTML、CSS 和原生 JavaScript，不使用框架、建置步驟、後端或付費服務。頁面需有遊戲標題、開始按鈕、一個佔位場景、一個可點擊互動點，以及可顯示一段測試文字的對話區。請支援手機窄螢幕、觸控操作和基本鍵盤操作；圖片可用 CSS 佔位色塊。請遵守 08_TECH_SPEC 的相對路徑與命名原則，列出每個新增／修改檔案的完整內容、放置路徑、手動測試步驟與已知限制。不要提前製作完整引擎、存檔或正式素材。

- **驗收標準：**
  - `index.html` 能載入，不出現空白頁。
  - 點「開始」後顯示佔位場景；點互動點後能顯示測試文字。
  - 手機直向畫面無主要控制項被裁切；按鈕可用手指操作。
  - 不需要安裝套件、建置工具或輸入 API 金鑰。
  - 產出已提交 Git，且可以明確回到此版本。
- **可能的失敗情況：** 路徑錯誤；AI 使用框架或外部 CDN；手機按鈕太小；程式只貼在聊天中卻未真正寫入 repository。
- **失敗時的處理方式：** 一次只修一種錯誤；請 AI 先讀取目前檔案，再回傳完整修正版；重新整理及重新部署後重測。若無法穩定運作，縮減到單一 HTML 檔先驗證，不加入更多功能。

## E01 — 核心引擎與資料載入

- **階段：** M2 核心引擎
- **目標：** 將原型整理成資料驅動的場景流程，建立場景切換、互動熱點、對話、白名單事件、錯誤提示和資源路徑基礎。
- **前置條件：** P01 在手機瀏覽器通過驗收；保留可回退的 Git commit。
- **輸入文件：** `03_GAMEPLAY_SPEC.md`、`05_SCENE_CATALOG.md`、`06_JSON_SCHEMA.md`、`08_TECH_SPEC.md`、P01 程式。
- **預期產出檔案：** 在現有結構上增補／整理 `js/` 中的引擎模組、`data/` 中最小測試 JSON，以及必要的錯誤提示；實際檔名由 AI 先提出並遵守 08_TECH_SPEC。
- **可直接交給 AI 的任務描述：**

  > 請以現有 P01 為基礎，設計並實作最小核心引擎。場景、熱點、對話和事件盡量由 JSON 資料驅動；事件只允許明確列出的安全動作，不執行 JSON 中的任意 JavaScript。請實作資料載入、場景切換、互動熱點、對話顯示、錯誤訊息及缺少資源時的降級。先提供檔案結構與資料流，再提交完整程式碼。使用相對路徑，考慮 GitHub Pages repository 子路徑。只使用一個測試場景與佔位素材，不要製作正式場景美術。附上逐步測試方法及修改檔案清單。

- **驗收標準：**
  - 由 JSON 載入至少一個場景、兩個熱點和一段對話。
  - 可由互動觸發已列入白名單的動作；未知事件或錯誤 JSON 顯示可理解的錯誤，不使整頁無聲失效。
  - 資源路徑在 repository 子路徑下仍能正確解析。
  - 無框架、無後端、無運行時 AI API。
  - 核心流程在手機瀏覽器實際測過，測試結果有紀錄。
- **可能的失敗情況：** JSON 欄位與 schema 不一致；事件邏輯散落在各處；使用根目錄絕對路徑；單一錯誤令遊戲卡死。
- **失敗時的處理方式：** 先用最小 JSON 重現問題；請 AI 比對 schema 和實際讀取欄位；先修復載入與路徑，再恢復其他模組。未通過驗收前不得開始大量正式素材製作。

## C01 — 第一章三個場景與互動流程

- **階段：** M3 第一章內容
- **目標：** 以佔位背景和資料完成第一章三個場景的可玩流程：潮痕灘 → 灰鐘台 → 下層記錄室。
- **前置條件：** E01 通過；場景切換、熱點、對話和資料載入已在測試場景穩定運作。
- **輸入文件：** `01_WORLD_BIBLE.md`、`02_STORY_BIBLE.md`、`03_GAMEPLAY_SPEC.md`、`05_SCENE_CATALOG.md`、`06_JSON_SCHEMA.md`、`07_ART_BIBLE.md`)。
- **預期產出檔案：** 第一章場景 JSON（放入核准的 `data/` 結構）、必要的場景索引或資源對照表；初期背景可以使用佔位色塊／簡單 SVG。
- **可直接交給 AI 的任務描述：**

  > 請依照正式文件，將第一章「潮痕灘 → 灰鐘台 → 下層記錄室」製作成符合 06_JSON_SCHEMA 的場景資料。先只做場景名稱、敘事文字、熱點位置與行為、場景出口及所需資源 ID；背景使用佔位素材。請保持世界觀規則，不新增未核准的重大設定。輸出每個 JSON 檔案完整內容、ID 引用表及手動驗收步驟。不要生成圖片，也不要在此任務擴寫正式角色立繪。

- **驗收標準：**
  - 三個場景可依設計順序進入，場景出口和互動熱點可操作。
  - 場景 ID、資源 ID 和事件名稱無重複或懸空引用。
  - JSON 可解析並符合 `06_JSON_SCHEMA.md`。
  - 使用者即使看不到正式圖片，仍可完成整段流程。
- **可能的失敗情況：** 場景跳轉斷鏈；AI 加入未定稿劇情；熱點在手機上太難點；JSON 引用不存在的素材。
- **失敗時的處理方式：** 先修正 ID 與場景連線；未決劇情回到故事文件確認；調整熱點尺寸和位置；對未製作資產保留清楚的佔位 ID。

## C02 — 第一章角色、劇情、道具與記錄

- **階段：** M3 第一章內容
- **目標：** 將第一章所需的角色、對話、道具、異常記錄碎片及事件條件整理成可供引擎讀取的資料。
- **前置條件：** C01 通過；E01 的對話與事件處理穩定；相關角色和劇情文件已確認有內容且沒有未決矛盾。
- **輸入文件：** `01_WORLD_BIBLE.md`、`02_STORY_BIBLE.md`、`03_GAMEPLAY_SPEC.md`、`04_CHARACTER_BIBLE.md`、`05_SCENE_CATALOG.md`、`06_JSON_SCHEMA.md`。
- **預期產出檔案：** 第一章所需的角色／對話／道具／記錄 JSON；必要的內容索引或 ID 清單。具體檔名依 schema 與技術規格決定。
- **可直接交給 AI 的任務描述：**

  > 請依據已確認的故事與角色設定，製作第一章所需的角色資料、對話節點、道具資料、異常記錄碎片和事件條件，全部符合 06_JSON_SCHEMA。保持角色語氣與世界觀一致；異常記錄只提供設計文件允許的線索，不提前揭露尚未揭露的長線謎底。請列出每個資料 ID、引用關係、取得條件和顯示位置。若故事或角色文件空白、缺漏或互相矛盾，先列出問題並停止編造該部分。

- **驗收標準：**
  - 對話節點可到達，選項／條件若有使用則有明確預設與無效狀態處理。
  - 道具或記錄能依流程取得，重複互動不造成不預期的重複獎勵。
  - 角色名稱、語氣、背景與正式設定一致。
  - JSON 可解析，所有 ID 引用存在；玩家可理解當前目標或下一步。
- **可能的失敗情況：** 劇情與世界觀衝突；對話分支無法返回；物品重複加入；把「殘響」寫成靈魂或全知回放。
- **失敗時的處理方式：** 以世界觀／故事文件為準回修；用簡短可重現的互動步驟檢查分支；為道具取得加入明確的狀態判斷；由負責人確認涉及核心謎團的文字。

## S01 — 第一章本機存檔與恢復

- **階段：** M4 存檔與體驗
- **目標：** 提供新遊戲、本機存檔／讀檔、刷新恢復、損壞存檔處理、寫入失敗提示與清除前確認。手動匯入／匯出為後續可選功能。
- **前置條件：** E01 資料與狀態結構穩定；C01、C02 已定義需要保存的場景、旗標、道具及記錄狀態。
- **輸入文件：** `03_GAMEPLAY_SPEC.md`、`06_JSON_SCHEMA.md`、`08_TECH_SPEC.md`、目前引擎與第一章資料。
- **預期產出檔案：** 存檔／讀檔模組、必要的存檔版本與驗證程式、存檔介面及相關說明文件。
- **可直接交給 AI 的任務描述：**

  > 請依 08_TECH_SPEC 為現有遊戲加入 localStorage 存檔與讀檔；本任務不要求手動匯入／匯出。保存足以恢復遊戲的場景 ID、劇情旗標、已取得道具／記錄及必要進度；不要保存不必要的暫時 UI 狀態。讀取前驗證資料結構與版本，遇到損壞或未知版本要顯示清楚訊息，且不可默默覆蓋有效存檔。明確告知 localStorage 只存在目前瀏覽器，不是雲端同步。提供測試步驟和失敗處理方式。

- **驗收標準：**
  - 進行互動後存檔，重新載入頁面可恢復場景和關鍵進度。
  - 無存檔、損壞存檔、未知版本都能安全處理；寫入失敗時有警告且當次遊玩可繼續。
  - 清除存檔前要求確認；取消操作不會清除有效進度。
  - 手動匯入／匯出明確列為後續可選功能，不阻擋第一章通關。
  - 清楚提示本機儲存限制，不宣稱雲端同步。
