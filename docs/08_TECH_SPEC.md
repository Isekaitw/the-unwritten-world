## 1. 架構總覽

採用**無建置步驟的靜態網站 + 原生 ES modules + JSON 內容資料**。

### 1.1 啟動流程

1. 瀏覽器開啟 `index.html`。
2. HTML 載入 `css/main.css`，再載入 `js/main.js`（使用 `type="module"`）。
3. `main.js` 初始化錯誤回報、DOM 參照、使用者設定和 UI 外殼。
4. 資料載入器以相對 URL 讀取 `data/*.json`，解析並驗證必要結構。
5. 資產索引建立背景圖與可選特效資產的對照表。
6. 狀態管理器載入本機存檔；若不存在或無效，建立新遊戲狀態。
7. 場景引擎載入起始場景、建立熱點並顯示場景 UI。
8. 玩家互動經由事件控制器執行資料定義的動作。
9. 每次成功的狀態變更都更新 UI，並在適當時機寫入本機存檔。

任何步驟失敗都應顯示可理解的錯誤或安全的替代畫面，不可只留下空白頁。

### 1.2 核心資料流

`HTML → main.js → data loader / validator → game state → scene renderer → UI`

玩家互動資料流：

`觸控/鍵盤 → input controller → hotspot/event handler → state changes → dialogue / scene transition / inventory / journal → renderer → save scheduler`

渲染程式不得直接修改 JSON 原始資料。JSON 是靜態內容定義；執行期間的玩家進度放在獨立的遊戲狀態物件中。

### 2.1 目錄規則

- GitHub Pages 固定使用 `main` 分支的 `/(root)`；根目錄 `index.html` 是入口頁，路徑和引用不得依賴開發伺服器的根目錄設定。
- `docs/` 只保存規格、交接與驗收文件，不由遊戲載入；不得再把 `docs/` 當成網站根目錄。
- `css/` 僅放樣式；不可把遊戲劇情或大量可變內容硬編碼在 CSS。
- `js/` 僅放程式邏輯；不得將劇情長文塞進 JavaScript 常數，除非是明確的錯誤回退訊息。
- `data/` 僅放 UTF-8 標準 JSON，不允許註解、尾隨逗號、函式或 JavaScript 表達式。
- `assets/` 放媒體資產。正式檔名需與 `07_ART_BIBLE.md`、`06_JSON_SCHEMA.md` 中的資產 ID 和路徑一致。
- `tests/` 放人工測試清單與可用的測試存檔；第一版不要求導入測試框架。
- 不要求安裝 Node.js、npm、Vite、Webpack 或其他建置工具。若未來新增，必須提供無建置的替代或另行修訂此文件。

## 3. HTML 與 JavaScript 模組規則

### 3.1 HTML 基本要求

- 設定 UTF-8、viewport 和適合手機的頁面縮放。
- 提供主選單、場景舞台、對話區、互動訊息、背包/日誌/設定面板的語意化容器。
- 重要按鈕使用真正的 `button` 元素；互動熱點應有可讀標籤和可聚焦能力。
- 不將所有 UI 畫在單張圖片裡；文字、按鈕、熱點與圖示應由 HTML/CSS/SVG 顯示。
- 不以 `user-scalable=no` 或禁止縮放的設定損害可及性。
- 若 JavaScript 失敗，頁面至少顯示「遊戲尚未成功載入，請重新整理或檢查資料」的基本訊息。

### 3.2 原生 ES modules

- 入口以 `<script type="module" src="./js/main.js"></script>` 載入。
- 模組使用明確的相對 import，例如 `import { loadJson } from "./data-loader.js";`。
- GitHub Pages 路徑大小寫敏感；檔名大小寫必須完全一致。
- 不使用 `eval`、`new Function`、遠端程式碼注入或 JSON 中的可執行內容。
- 本機測試請使用能提供 HTTP 的靜態檔案預覽工具或 GitHub Pages。直接以 `file://` 開啟時，瀏覽器可能因模組或 fetch 安全限制拒絕載入；這不等於部署版本必然失敗。

### 3.3 非同步初始化

啟動程序必須等待必要 JSON 成功載入與驗證後才進入可玩狀態。不得讓使用者在資料尚未就緒時觸發場景事件。載入失敗時顯示明確訊息和「重新嘗試」操作；重試不應建立重複的事件監聽器。

**測試：** 故意把一個必要 JSON 路徑改錯，確認頁面顯示錯誤而非無限轉圈或空白；恢復路徑後重新整理，確認能正常載入。

## 4. JSON 資料載入與驗證

### 4.1 正式資料集合

資料檔放在 `data/`，格式、欄位和 ID 以 `06_JSON_SCHEMA.md` 為準：

- `game.json`：遊戲版本、起始場景、全域設定。
- `scenes.json`：場景 ID、背景、圖層、熱點、出口和場景設定。
- `characters.json`：角色 ID、顯示名稱與角色資料。
- `dialogue.json`：對話節點、台詞、選項與分支。
- `events.json`：可執行的白名單事件定義。
- `items.json`：物品資料。
- `quests.json`：任務、線索或日誌相關資料。
- `assets.json`：資產 ID、相對路徑與資產類型。

### 4.2 載入器規則

- 使用 `fetch(new URL(relativePath, import.meta.url))` 或統一的專案基底路徑函式處理模組相對路徑；不可假設網站必定部署在網域根目錄。
- 每個回應都檢查 `response.ok`；HTTP 404 不會自動視為 JavaScript 例外。
- 解析 JSON 時捕捉語法錯誤，訊息需包含檔名或路徑。
- 必要資料失敗則停止進入遊戲並提供重試；可選資料失敗則採用文件定義的空集合或替代內容，並記錄警告。
- 不使用 `no-cors` 迴避錯誤；該模式無法讓程式讀取正常的 JSON 回應內容。
- 可在同一頁生命週期中快取已成功載入的資料，避免每次開關 UI 都重抓 JSON。
- 不應把玩家進度寫回原始 JSON；靜態網站沒有可靠的方式覆寫 GitHub 上的遊戲資料。

### 4.3 驗證器最低要求

至少驗證：頂層型別、必填欄位、ID 唯一性、被引用的場景/角色/對話/事件/物品 ID 存在、事件動作屬於白名單、資產路徑是允許的相對路徑、場景出口目標存在。遇到錯誤時列出檔名、資料 ID、欄位和原因。

驗證器不得擅自「猜測」缺失資料，也不得把未知事件轉成可執行程式碼。未知的可選欄位可依 06 的政策警告或拒絕；不可在不同模組採用不同標準。

**測試：** 複製一份測試資料，分別製造無效 JSON、重複 ID、不存在的場景引用、未知事件動作和錯誤資產路徑，確認每一項都有可定位的錯誤訊息。

## 5. 場景引擎

### 5.1 場景舞台

場景由固定比例的舞台容器組成，容器內有背景層、可選中景/前景層、特效層和互動熱點層。建議以 CSS `aspect-ratio` 或等效的比例容器維持背景構圖，再以 `object-fit: cover` 或符合美術構圖的方式顯示圖片。不得因裝置比例不同而拉伸人物或遺跡。

- 背景圖是場景視覺的主要來源。
- 視差圖層和粒子層皆為可選；沒有該資產時場景仍可正常遊玩。
- 熱點以透明按鈕/可聚焦 DOM 元素疊在場景上；熱點位置以場景設計座標或比例座標記錄，不能直接以單一手機像素座標固定。
- UI 面板與場景舞台分離，避免舞台縮放導致對話文字被裁切。

### 5.2 進入場景流程

1. 確認目標場景 ID 存在。
2. 將目前場景的可選暫態效果停止，避免上一場景的動畫殘留。
3. 讀取背景和圖層資產；背景可顯示載入中的中性底色。
4. 若背景載入失敗，顯示可讀的場景替代畫面，仍可使用文字版場景描述與可操作的熱點。
5. 清除上一場景的熱點和監聽器，依新場景資料建立熱點。
6. 更新目前場景 ID 和場景進度。
7. 執行資料明確指定的進場事件（若有且通過驗證）。
8. 顯示場景標題/描述，安排存檔。

### 5.3 場景離開流程

- 阻止舊場景的熱點在切換後繼續被觸發。
- 停止或取消場景專屬動畫。
- 清理臨時 DOM 與事件監聽器。
- 更新狀態後切換到新場景。
- 不能因單純重新渲染同一場景而重複發放物品、重複執行一次性事件或重複增加線索。

### 5.4 場景狀態與回訪

至少保留目前場景 ID、已造訪場景集合、已調查熱點/已執行一次性事件的 ID。是否重置熱點、是否允許重複對話、事件能否重複執行由資料定義，不得由渲染器猜測。

**測試：** 在第一章三個場景間往返，確認背景、熱點、標題和對話正確；連續快速點擊出口，確認不會重複切場或重複發獎勵；回訪已調查場景，確認狀態符合玩法規格。

## 6. 熱點、事件、對話與狀態資料流

### 6.1 熱點

每個熱點使用穩定的 ID，並引用事件或對話 ID。熱點資料至少要能表達：顯示名稱/無障礙標籤、位置、可見條件、可互動條件、動作類型和目標 ID。實際欄位依 06 為準，不得在程式端另造平行格式。

觸控時應有足夠大的有效命中區域；視覺上可以小，但透明點擊區需考慮手指誤差。若熱點被條件隱藏或禁用，必須同時移除鍵盤焦點與點擊能力，不能只把透明度設為零。

### 6.2 事件執行器

事件是資料驅動的有限動作清單，不是可執行腳本。第一版允許的動作應由 06 明確列出並由程式以白名單實作，例如：

- 顯示文字或開啟對話。
- 取得或使用指定物品。
- 新增日誌線索或更新任務旗標。
- 切換至指定場景。
- 設定布林旗標或簡單數值狀態。
- 顯示提示、播放可選音效（若已實作）。

每個動作都要驗證目標 ID、前置條件與一次性規則。未知動作必須拒絕執行並輸出資料錯誤；不得忽略後繼續假裝成功，也不得呼叫 JSON 提供的函式或任意方法。

### 6.3 建議的事件生命週期

1. 玩家啟動熱點。
2. 控制器確認熱點存在、可見、可用，並阻止短時間重複觸發。
3. 事件引擎依序評估條件。
4. 若條件不成立，顯示資料指定的提示或安全預設訊息。
5. 若條件成立，依順序執行白名單動作；一次性事件成功完成後才標記為已完成。
6. 更新背包、日誌、任務旗標、對話或場景狀態。
7. UI 依狀態重新渲染。
8. 存檔管理器排程保存。

若動作序列中途失敗，不應將整個事件標記為成功。對可能產生重複副作用的動作，需採用先驗證再執行、或明確的完成旗標，以免重試重複發獎勵。

### 6.4 對話引擎

- 對話資料以 ID 引用，不以陣列位置或顯示文字作唯一識別。
- 對話節點可引用角色 ID、台詞、選項與下一節點/事件。
- 顯示選項前評估其條件；不可用 CSS 隱藏仍可被鍵盤或觸控操作的選項。
- 選擇後記錄必要的旗標或選擇結果，再移至下一節點。
- 對話 ID 缺失、循環或目標不存在時，顯示錯誤回退訊息並允許退出，不可凍結整個遊戲。
- 玩家需可透過明確的按鈕關閉/繼續對話；不得只要求精準點擊台詞文字。

**測試：** 點擊一個熱點，確認它只觸發所引用的事件；檢查事件條件成立/不成立、一次性事件重複點擊、對話選項分支、對話結束後 UI 是否恢復，以及存檔重載後旗標是否仍一致。

## 7. 視差、粒子、霧氣與其他效果

### 7.1 原則

特效服務於氣氛，不可承載唯一線索、不可成為必要命中區域，也不可影響遊戲邏輯。先確保角色移動、碰撞、鏡頭、場景邊界與互動回饋可用，再逐項加入視差、霧氣、粒子與光效。

### 7.2 視差實作

- 以 CSS transform 或少量 JavaScript 更新圖層位移；優先使用 `transform`，避免每影格反覆改變版面尺寸。
- 位移幅度應小、受限且不影響熱點對應位置。
- 支援觸控拖曳或裝置傾斜並非必要；第一版建議使用緩慢自動位移或簡單指標移動，且必須有關閉/減弱方式。
- 不要求陀螺儀權限。若未來使用裝置方向感測，必須偵測支援、處理權限拒絕，並提供不使用感測器的替代方案。
- 在小螢幕上以舞台座標計算圖層位置，避免圖層移出可視區或露出未填滿的空白。

### 7.3 粒子、霧氣與光效

- 優先使用 CSS 漸層、低數量 DOM 粒子或靜態圖層；只有在有明確效益時才考慮 Canvas。
- 限制同時活動的粒子數與動畫數；不得為每一個粒子建立高頻定時器。
- 動畫不可攔截熱點操作；特效層設為不接收指標事件。
- 尊重 `prefers-reduced-motion: reduce`，並提供遊戲內的「減少動態效果」設定。
- 切換場景或頁面進入背景時，停止非必要動畫；回到前景再視需要恢復。
- 音效屬可選功能；首次播放可能受瀏覽器自動播放政策限制，必須由玩家操作後才嘗試播放，且失敗不阻擋遊戲。

### 7.4 降級策略

依序降級：完整特效 → 降低粒子/動畫 → 靜態圖層 → 單張背景。即使關閉全部特效，場景、熱點、對話、任務和存檔都必須正常。

**測試：** 開啟與關閉減少動態效果，確認熱點位置不變且仍可操作；在支援與不支援的瀏覽器中檢查動畫；切場後確認沒有上一場景殘留的粒子或動畫。

## 8. UI、手機版面與觸控操作

### 8.1 介面原則

- 手機優先，先支援直向；橫向與平板版面在可用空間充足時調整，不可因旋轉而遺失遊戲狀態。
- 使用響應式 CSS、彈性尺寸與安全區域變數；避免以單一裝置像素硬寫所有座標。
- 對話文字有足夠行距與對比；按鈕標籤清楚，不只依賴顏色或圖示傳達意義。
- 重要互動區建議至少約 44×44 CSS px；熱點命中區需依場景比例調整並在真機檢查。
- 支援觸控與滑鼠/鍵盤作為輔助輸入。互動控制不能只依賴 hover。
- 面板開啟時需有明確關閉方式；避免遮住主要操作而沒有退出途徑。
- 使用 `env(safe-area-inset-*)` 時需保留一般瀏覽器的 fallback。

### 8.2 觸控事件

- 優先採用 Pointer Events 或一致的 click 行為，避免同時綁定 touchend 與 click 導致一次點擊執行兩次。
- 不攔截整個頁面的所有手勢；只在需要的舞台區處理拖曳。
- 除非有必要，避免使用 `preventDefault()` 阻止頁面正常捲動。
- 快速重複點擊要有保護，但不可讓正常的連續對話操作感到延遲。
- 互動按鈕需具備 focus 樣式與可讀名稱；對話選項可用鍵盤選擇。

### 8.3 版面測試

**測試：** 至少檢查手機直向、手機橫向、平板直向/橫向及桌面縮窄視窗。確認沒有橫向溢出、主要按鈕不被瀏覽器安全區遮住、對話可閱讀、熱點可觸及，且旋轉裝置不會重置進度。

## 9. 遊戲狀態與 localStorage 存檔

### 9.1 存檔範圍

存檔至少包含：存檔格式版本、遊戲內容版本（若有）、目前場景 ID、已造訪場景、已調查熱點/已完成一次性事件、玩家旗標、背包、任務/日誌進度、已知線索、必要的對話分支結果和最後保存時間。精確欄位由 06 與遊戲狀態實作共同定義，禁止把 DOM 結構直接序列化成存檔。

### 9.2 儲存策略

- 建議使用固定 key，例如 `unwrittenWorld.save.v1`；key 名稱與版本由 `config.js` 集中管理。
- 存檔以 `JSON.stringify` 序列化，讀取後以 `JSON.parse` 解析，再通過結構與版本驗證。
- 使用 `try/catch` 處理 `localStorage` 不可用、配額不足、安全限制、JSON 損壞等情況。
- 在重要狀態變更後排程存檔，短時間多次變更應合併；另在場景切換、重要線索取得和設定變更後保存。
- 不要在每個動畫影格、每次滑鼠移動或每個字元顯示時寫入存檔。
- 遊戲內顯示「已保存」只可在寫入成功後顯示；失敗時顯示本機存檔失敗提示，並建議匯出 JSON 備份。
- localStorage 通常依來源/網域隔離；從不同網址、不同部署來源或清除網站資料後，存檔可能不可見或遺失。
- localStorage 不是雲端同步或加密儲存，不應放密碼或敏感資料。

### 9.3 新遊戲、讀取與重置

- 「新遊戲」需明確提示是否覆蓋現有進度。
- 「繼續遊戲」只載入通過驗證且版本可接受的存檔。
- 「重置進度」需二次確認，並只刪除本遊戲指定 key，不清除整個網站的所有資料。
- 若存檔版本較舊，只有在存在明確遷移函式時才自動遷移；否則保留原始資料並提示匯出備份，不能靜默覆蓋。

**測試：** 取得一項線索後重新整理，確認進度仍在；使用無效 JSON 或錯誤版本覆蓋測試存檔，確認遊戲能提示並安全啟動新狀態；模擬 localStorage 寫入失敗，確認遊戲仍可玩且顯示警告。

## 10. JSON 存檔匯出與匯入

### 10.1 匯出

- 由玩家主動操作觸發。
- 將目前存檔狀態序列化成 JSON Blob，透過暫時建立的下載連結下載檔案；建議檔名包含遊戲代號和日期。
- 匯出內容只包含必要遊戲進度、版本資訊和時間，不包含執行中的函式、DOM 或瀏覽器內部物件。
- 匯出失敗時提供明確訊息，並保留原本 localStorage 存檔。

### 10.2 匯入

- 使用 `<input type="file" accept=".json,application/json">` 讓玩家自行選擇存檔檔案；此操作需要玩家明確挑選檔案，不需要額外的瀏覽器權限。
- 讀取後先解析 JSON，再檢查頂層結構、存檔版本、欄位型別、ID 是否存在於目前內容資料、數量與字串長度是否合理。
- 不得對匯入資料使用 `eval` 或將字串插入 `innerHTML`。文字應使用 `textContent` 或安全的 DOM 建立方式。
- 匯入前顯示覆蓋警告；驗證成功後才替換目前存檔，失敗時保留原進度。
- 不支援的較新版本不可強制載入；較舊版本只可由明確遷移程序處理。
- 匯入的存檔不是可信任來源；即使它是 JSON，也必須視為外部輸入。

### 10.3 匯入/匯出測試

1. 匯出存檔，確認下載檔案是可讀的 JSON。
2. 清除測試用進度後匯入，確認場景、物品、旗標與日誌恢復一致。
3. 匯入空檔、亂碼、缺欄位、未知場景 ID、錯誤版本和超大檔案，確認都會被拒絕且原存檔不受影響。
4. 在手機瀏覽器確認下載和檔案選擇流程可完成；不同瀏覽器的下載 UI 可能不同，需分別實測。

## 11. 相對路徑、資源 URL 與 GitHub Pages

### 11.1 專案可能部署在子路徑

GitHub Pages 專案網站通常會位於類似 `https://<owner>.github.io/<repository>/` 的子路徑，而非網域根目錄。所有專案資源必須支援子路徑。

- **禁止**在 HTML、CSS、JSON 或 JavaScript 中隨意使用以 `/` 開頭的專案資源路徑，例如 `/data/scenes.json`，因為它會指向網域根目錄。
- 在 HTML 中使用 `./css/main.css`、`./js/main.js`。
- 在 JS 模組中使用相對 import。
- 資料和資產路徑集中處理；不要在不同模組各自拼接 repository 名稱。
- CSS 的 `url(...)` 相對於該 CSS 檔案所在位置解析；JSON 裡的資產路徑則由 asset manager 以約定的基準目錄解析，兩者不可混淆。
- URL 路徑大小寫必須與 GitHub 實際檔名一致；避免空格、非 ASCII 字元和含糊的相對路徑。

### 11.2 路徑解析建議

建立單一路徑工具，從已知的入口或模組 URL 推導專案基底，再解析資料/資產路徑。禁止依賴使用者當前瀏覽器網址中的任意 query string 來推導資源位置。所有 JSON 資料的資產路徑基準應由 06 和 `assets.json` 明確定義。

### 11.3 GitHub Pages 限制

- GitHub Pages 提供靜態網站，不會執行伺服器端程式、資料庫、Node.js 後端或 API 路由。
- 玩家在遊戲中修改的資料不會寫回 repository，也不會自動同步到其他裝置。
- 部署需要網路載入網站和未快取的檔案；GitHub Pages 不是自動離線套件。
- 瀏覽器快取、localStorage、下載行為與 Service Worker 支援會因瀏覽器和來源而異。
- 發布後要確認 repository 的 Pages 設定指向正確 branch/folder，並使用實際發布網址測試子路徑。
- 若 Pages 建置/發布尚在進行，不能只因 GitHub commit 成功就宣稱網站已上線。

**測試：** 從實際 GitHub Pages 網址開啟開發者工具/瀏覽器錯誤訊息，確認 HTML、CSS、JS、JSON 和圖片都沒有 404；特別檢查網站是否位於 repository 子路徑時仍可正常載入。

## 12. 離線友善與 Service Worker

### 12.1 第一版策略

第一版**不把 Service Worker 列為啟動或遊戲流程的必要條件**。先確保網路正常時所有功能可靠，並讓核心邏輯不依賴外部 API。可以使用瀏覽器正常快取，但不得把普通快取宣稱為完整離線支援。

### 12.2 何時才加入 Service Worker

只有在下列條件都滿足後才加入：
1. 基本場景、資料載入、存檔和匯入/匯出已通過測試。
2. 有明確的離線需求和要快取的檔案清單。
3. 使用 HTTPS 的實際部署環境已確認支援。
4. 有版本更新、舊快取清理、快取失敗回退與測試計畫。
5. 能在手機瀏覽器實測首次線上載入、重新開啟、斷網、更新版本和清除網站資料等流程。

### 12.3 若實作 Service Worker

- 需要新增根目錄或適當路徑下的 `sw.js`，以及在入口程式中註冊的程式碼；路徑必須與 GitHub Pages 子路徑相容。
- Service Worker 需要安全來源（通常為 HTTPS；localhost 可供開發測試）。
- 快取版本需明確命名；新版本安裝成功後清理舊快取，但不得刪除不屬於本遊戲的快取。
- 對 HTML、CSS、JS、JSON 和圖片採用清楚的快取策略；不要無條件快取所有請求或外部網站內容。
- 更新後需測試舊資料快取與新程式版本是否相容，避免 JS 和 JSON 版本混搭。
- Service Worker 安裝或快取失敗時，網站仍應能以一般網路載入方式運作。
- 離線首次開啟尚未快取的網站不可能憑空載入資源；必須先成功線上載入並完成快取。

**測試：** 未加入 Service Worker 前，標記離線完整遊玩為「未提供/未驗證」。加入後須分別記錄首次載入、已快取後斷網、更新部署後、清除快取後的實測結果。

## 13. 錯誤處理與除錯流程

### 13.1 錯誤類型

- 啟動錯誤：入口模組未載入、必要資料失敗。
- 資料錯誤：JSON 語法錯誤、欄位缺失、引用 ID 不存在。
- 資產錯誤：圖片或音訊 404、格式不支援、解碼失敗。
- 執行錯誤：事件動作失敗、無效場景轉換、對話節點缺失。
- 儲存錯誤：localStorage 被封鎖、配額不足、存檔格式損壞。
- 匯入錯誤：檔案無法讀取、版本不相容或資料不安全。
- 裝置/效能問題：記憶體不足、動畫卡頓、旋轉後版面錯誤。

### 13.2 訊息原則

- 面向玩家：用簡短、可理解的繁體中文說明問題和可採取的下一步。
- 面向開發：在 console 記錄錯誤類型、檔案/資料 ID、操作階段和必要的堆疊資訊。
- 不記錄不必要的個人資料；不顯示整份存檔或過量內部狀態。
- 可恢復錯誤要提供重試或回到安全畫面的方式；不可恢復的單一資料錯誤不應摧毀既有存檔。
- 不可用空的 `catch {}` 靜默吞掉錯誤。

### 13.3 除錯步驟（非程式人員可操作）

1. 記下操作前做了什麼、預期發生什麼、實際發生什麼。
2. 重新整理一次，確認問題是否可重現。
3. 若畫面有錯誤訊息，完整抄下訊息；若可使用瀏覽器開發者工具，檢查 Console 和 Network。
4. 先檢查最近修改的檔案、JSON 逗號/括號、ID 和大小寫，再檢查資源路徑。
5. 一次只改一項；不要同時重寫多個模組。
6. 修正後重跑該功能的測試清單，並回歸測試場景切換、存檔和匯入/匯出。
7. 在 commit 訊息或測試紀錄中寫下修改和結果；沒有實際重測就標記「待驗證」。

### 13.4 開發除錯工具

可提供開發模式開關，顯示目前場景 ID、載入資料狀態和存檔狀態。正式版本預設關閉，不能讓玩家透過 UI 隨意改寫重要進度或執行任意事件。

**測試：** 人為製造一項資料錯誤和一項圖片錯誤，確認玩家畫面有提示、Console 有可定位資訊，並確認修復後可正常恢復。

## 14. 效能與手機記憶體限制

### 14.1 基本原則

手機和平板的記憶體、GPU、CPU 和瀏覽器分頁生命週期各有差異，不設定虛假的跨裝置硬性保證。以低記憶體裝置可玩、長時間不累積 DOM、特效可關閉為設計目標。

### 14.2 圖片與資產

- 背景圖的解析度依實際舞台尺寸和美術規範選擇，不要將數十 MB 的原始圖直接當作網頁背景。
- 優先採用壓縮過的 WebP；若需相容性回退，提供經驗證的替代格式。
- 單張圖片尺寸與檔案大小應在資產清單記錄，超出專案目標需先確認必要性。
- 不要一次預載整個遊戲所有章節的大量圖片；只載入目前場景及合理的下一場景資產。
- 場景切換時釋放不再使用的 DOM 引用和動畫；不要假設手動清空引用會立刻讓瀏覽器釋放記憶體。
- 避免重複載入同一資產、建立重複監聽器或不斷追加不可見的對話元素。

### 14.3 動畫與渲染

- 動畫優先使用 CSS transform/opacity。
- 避免無必要的全螢幕模糊、大面積 filter、持續重繪和多層半透明覆蓋。
- 非必要動畫使用頁面可見性狀態暫停；切換場景時清除前場景動畫。
- 不在每一影格執行 JSON 搜尋、完整 UI 重繪或 localStorage 寫入。
- 低效能模式應減少粒子和動態層，而不是降低文字可讀性或移除必要按鈕。

### 14.4 效能驗收

**測試：** 在至少一台實際手機與一台平板（若可取得）連續探索 10 分鐘、切換場景多次、開關面板並重複對話；觀察卡頓、頁面重載、熱點延遲、記憶體相關崩潰和動畫殘留。記錄裝置、瀏覽器、日期與結果。若沒有實際裝置測試，必須標記未驗證。

## 15. 無網路、缺圖和資料錯誤的降級行為

| 情況 | 必須的行為 | 不允許 |
|---|---|---|
| 網路中斷，必要資料尚未載入 | 顯示載入失敗與重試提示 | 假裝已載入或無限轉圈 |
| 網路中斷，必要資料已載入 | 目前已載入內容盡可能繼續使用；未載入資產顯示替代內容 | 宣稱完整離線可玩，除非已驗證 |
| 背景圖缺失 | 顯示該場景的中性背景、標題和文字描述；保留可用熱點 | 整個場景變空白且無法操作 |
| 可選前景/粒子缺失 | 省略該層並記錄警告 | 阻止場景啟動 |
| 必要 JSON 無法解析 | 停止依賴該資料的流程，顯示檔名與錯誤摘要 | 靜默使用猜測資料 |
| 非必要 JSON 失敗 | 僅在有明確預設值時使用空集合/替代 UI | 假裝資料內容完整 |
| 熱點引用不存在 | 不建立該熱點，顯示開發警告；必要主線不可無聲卡死 | 觸發未知事件 |
| 存檔損壞 | 保留原始資料供匯出/恢復選項，提示建立新存檔 | 自動覆寫唯一存檔而不通知 |
| 匯入檔不合法 | 拒絕匯入並保留目前進度 | 部分匯入後破壞狀態 |
| 特效不支援/效能過低 | 關閉特效，保留基本場景與互動 | 將特效設為主線必要條件 |

降級畫面需使用本地 HTML/CSS，不可依賴另一張網路圖片來顯示「圖片載入失敗」。

## 16. 安全與隱私最低要求

- 不收集玩家帳號、密碼或個人識別資料；不加入追蹤分析服務，除非另行明確核准並修訂文件。
- 不使用外部 API 作為遊戲啟動或主線推進的必要條件。
- 所有由 JSON 或匯入存檔提供的文字都視為不可信資料；使用 `textContent` 或安全 DOM API 顯示。
- 不使用 `innerHTML` 插入未經處理的玩家/匯入資料。
- 不執行 JSON 中的腳本、函式、URL scheme 或任意事件名稱。
- 只接受預期的相對資產路徑，拒絕 `javascript:`、不受允許的外部 URL、路徑穿越字串或不符合規格的資產位置。
- 存檔只存在玩家本機；清除網站資料、使用不同瀏覽器或不同網站來源都可能導致無法取得，需鼓勵定期匯出備份。

**測試：** 匯入包含 HTML 標籤字串的測試存檔，確認它只以文字顯示，不執行標籤；匯入未知事件或外部腳本路徑，確認驗證器拒絕。

## 17. 測試流程與驗收標準

### 17.1 測試層級

1. **資料檢查：** 所有 JSON 可解析，ID 唯一，引用存在，資產路徑正確。
2. **模組測試：** 資料載入、狀態更新、事件執行、存檔和匯入/匯出各自可單獨驗證。
3. **流程測試：** 從開啟遊戲到第一章三個場景完成主要探索流程。
4. **回歸測試：** 修改任一模組後重跑核心路徑、場景切換和存檔測試。
5. **裝置測試：** 手機、平板、直向/橫向、觸控和必要的輔助鍵盤操作。
6. **部署測試：** 實際 GitHub Pages 網址與子路徑資源載入。
7. **降級測試：** 缺圖、無效 JSON、存檔失敗、減少動態效果和網路中斷情境。

### 17.2 第一個可玩版本的最低驗收清單

- [ ] GitHub Pages 實際網址可開啟入口頁。
- [ ] CSS、ES modules、八份必要資料 JSON 和需要的資產沒有路徑 404。
- [ ] 第一章起始場景能載入並顯示標題、背景或缺圖替代畫面。
- [ ] 潮痕灘、灰鐘台、下層記錄室可依設計流程切換。
- [ ] 熱點可觸控，且不會一次點擊觸發兩次。
- [ ] 事件條件、一次性事件、物品、線索和對話選項按資料正確執行。
- [ ] 場景切換不重複發放物品，不留下舊場景熱點或動畫。
- [ ] localStorage 存檔成功後，重新整理可恢復進度。
- [ ] 無效存檔不會靜默覆蓋有效進度。
- [ ] JSON 匯出和匯入可以完成往返，無效檔案會被拒絕。
- [ ] 減少動態效果開啟時，核心玩法仍完整。

- [ ] Console 沒有未處理錯誤；必要的資料警告均可定位。
- [ ] 已記錄測試日期、裝置/瀏覽器、步驟、預期結果、實際結果與未解問題。

每個功能以以下格式記錄：

- 操作步驟：

## 18. 非程式人員的開發與發布流程

### 18.1 以手機或平板開發

1. 在 GitHub App 或瀏覽器登入 GitHub，開啟專案 repository：`Isekaitw/the-unwritten-world`。

1. 將程式、資料與資產提交到 `main` 分支，並確認入口 `index.html` 位於 repository 根目錄。

3. 在 Build and deployment 設定中選擇從分支部署，選擇 `main` 和 `/(root)`（若專案之後改採其他資料夾，必須同步修訂本文件）。
4. 儲存設定並等待 GitHub Pages 顯示部署完成。提交成功不代表部署已完成。
5. 開啟 GitHub Pages 顯示的實際網址；不要自行假設網址或路徑。
6. 在手機瀏覽器重新載入網站，測試起始場景、熱點、對話、存檔、匯出/匯入和缺圖替代畫面。
7. 檢查是否因子路徑造成 CSS、JS、JSON 或圖片 404。修正後再提交並等待重新部署。
8. 每次發布後記錄 commit、網址、測試日期、裝置和結果；未測試的項目明確標為「未驗證」。

### 18.3 AI 開發任務的標準要求

每次請 AI 修改程式時，附上以下要求：

- 先閱讀本文件和相關規格，遵守既有目錄與模組責任。
- 不新增付費 API、後端、資料庫、登入或必要建置步驟。
- 不自行更改 JSON schema；若必須改，先列出受影響文件和遷移方式。

- 提供每個修改檔案的完整內容或明確 patch，列出檔名。
- 提供可由非程式人員照做的測試步驟與預期結果。
- 分開標示「已實作」「已測試」「未驗證」「後續建議」。
- 不得聲稱已操作 GitHub、已部署、已生成圖片或已實測，除非確實執行並提供可查證結果。
