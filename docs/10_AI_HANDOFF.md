所有任務都必須遵守以下規則。若某項要求與任務衝突，先停止該部分並回報，不可自行越權改規格。

6. **不任意更改正式設定：** 世界規則、年代、角色身分、劇情因果、既定 ID、資料契約及已使用的存檔欄位，不可因單次生成方便而改寫。
7. **不假裝測試：** 只可報告實際執行的測試。沒有執行的項目標示「未測試」；無法測試的項目要說明原因和人工操作步驟。

9. **不無故重寫整個專案：** 只改任務所需的最小範圍，詳見第 9 節。
10. **不把建議當定案：** 規格中標示為建議、待決或後續的內容，不得在沒有說明的情況下變成不可逆的硬性依賴。

13. **保護帳戶與資料：** 不得把密碼、個人存取權杖、API key、私人資料或其他秘密寫進程式、JSON、Issue、截圖或公開 repository。
14. **不隱藏未完成事項：** 未解決問題、暫時替代品、待人工確認事項及風險都要明確列出。
15. **尊重原創與授權：** 不直接複製他人作品、角色、商標、音樂或受限制的風格；記錄外部素材來源、授權及必要署名資訊。

## 4. 規格衝突處理流程

遇到矛盾時，依序處理：

1. **停住衝突部分：** 不要先寫程式、JSON 或圖片來掩蓋矛盾。與衝突無關、可安全獨立完成的工作可以繼續。
2. **列出證據：** 記錄每份衝突文件的路徑、章節標題，以及造成矛盾的簡短摘要。引用要準確，不要只寫「文件不一致」。
3. **判斷衝突領域：** 世界事實看 01；劇情因果與揭露看 02；角色事實看 04；玩法行為看 03；場景與出口看 05；資料格式看 06；程式實作看 08；視覺素材看 07；任務順序看 09。
4. **保護跨系統相容性：** ID、已保存資料欄位、現有路徑和已使用引用不可單方面更名或刪除。
5. **提出最小修正：** 提供建議採用的方案、受影響檔案、相容性風險及是否需要遷移存檔。
6. **需要決策時請使用者確認：** 尤其涉及已定案世界觀、角色、劇情結局、技術邊界、付費依賴或大量檔案重構。
7. **同步文件：** 決策確定後，先修訂負責該領域的規格，再更新相關 JSON、程式或素材，避免文件與實作長期分歧。
8. **留下紀錄：** 在交付報告中記錄衝突、決策、受影響檔案和仍待處理項目。

若只是低風險的命名或排版問題，且不改變 ID、資料結構或既定內容，可直接採用一致的最小修正，並在交付報告說明。若無法確定，不得把推測寫成既定事實。

## 6. 程式修改的標準交付格式

每次修改 HTML、CSS、JavaScript、設定或部署檔案，都必須提供：

1. **修改檔案清單：** 每個檔案的完整 repository 相對路徑。
2. **修改摘要：** 每個檔案改了什麼、為什麼改，以及與任務目標的關係。
3. **修改範圍：** 新增／修改／刪除的檔案分開列出；若刪除檔案，說明理由與影響。
4. **實作方式：** 解釋關鍵行為、錯誤處理、相容性及可能限制；不要只貼大段程式碼而不說明。
5. **測試紀錄：** 測試名稱、實際操作或命令、環境、結果、日期；未執行的項目寫「未測試」。
6. **人工測試步驟：** 使用者若只有手機／平板，提供可照著點的步驟，不要求使用者輸入命令列指令作為唯一驗收方法。
7. **回退方式：** 說明如何還原本次變更，或指出可回退到的 commit。不得要求使用者不理解就執行破壞性命令。
8. **未解決問題：** 明列已知缺陷、暫時方案、待確認事項及後續建議。
9. **交付狀態：** 使用「已產出」「已提交」「測試通過」「手機實測」「已發布」等準確狀態，不能把它們混為一談。
10. **提交資訊：** 若確實提交至 Git，列出 commit SHA、分支和檔案連結；若沒有提交，明確寫「尚未提交」。

### 程式碼交付方式

- 有 repository 寫入能力時，優先直接修改目標檔案並回讀驗證。
- 若只能提供程式碼，必須提供完整目標路徑、完整檔案內容或清楚標示的最小差異，以及使用者可照做的套用步驟。
- 不要只說「把這段放到適當位置」；必須說明檔名、定位方式及前後關係。
- 若提供完整檔案替換，先檢查現有內容，說明替換可能覆蓋哪些既有功能。
- 不要把示範碼、偽程式碼或未接線的函式宣稱為已整合功能。

## 7. JSON 與美術素材的標準交付格式

### 7.1 JSON 交付

新增或修改 JSON 時，必須交付：

- 檔案路徑，例如 `data/scenes.json`。
- 變更的頂層物件／陣列項目及其用途。
- 新增、修改、刪除的 ID 清單。
- 所有被引用的場景、角色、事件、任務、道具和資產 ID 是否存在。
- 所有資產路徑是否能對應到真實檔案或明確標示的待製作資產。
- JSON 語法檢查結果；可用時再做 schema／引用驗證。
- 與 `docs/06_JSON_SCHEMA.md` 不一致的地方，以及是否需要先修訂 schema。
- 未測試或無法驗證的引用。

JSON 必須是標準 JSON：雙引號、沒有註解、沒有尾隨逗號、沒有 JavaScript、函式、`undefined`、`NaN` 或 `Infinity`。不得為了快速實作自行新增 schema 未定義欄位；若確實需要新欄位，先提出最小 schema 修訂並更新相關文件。

### 7.2 美術素材交付

- 資產 ID。
- 預定檔案路徑與實際檔案路徑。
- 素材用途與對應場景／角色。
- 對應的 `docs/07_ART_BIBLE.md` 規格。
- 圖片格式、尺寸、比例及是否透明（如適用）。
- 生成工具或來源、生成日期，以及可用的提示詞／來源紀錄。
- 授權或使用條件是否確認；未確認時標示「授權待確認」，不得當作可發布素材。
- 視覺驗收結果：構圖、世界觀一致性、角色一致性、錯字／假文字／浮水印、手機裁切及檔案可讀性。
- 資產是否已放入 repository、是否已在 `data/assets.json` 登錄、是否已由遊戲實際載入。
- 缺少正式素材時使用什麼佔位方案。

不得只交付提示詞就說圖片已製作；不得只看到生成結果就說已下載、已上傳或已整合。每個狀態都要有對應證據。

## 8. 檔案命名、ID 與資源路徑

### 8.1 檔案命名

- 檔名優先使用小寫英文字母、數字和底線；副檔名符合內容格式。
- GitHub Pages 唯一發布來源為 `main` 分支的 `/(root)`；遊戲入口預定為根目錄 `index.html`。
- 規格文件放在 `docs/`，使用既定編號，例如 `docs/10_AI_HANDOFF.md`；`docs/` 不作為網站根目錄。
- 遊戲資料放在 `data/`，程式放在 `js/`，樣式放在 `css/`，媒體資源放在 `assets/`。若實際 repository 尚未建立這些檔案，只記錄缺漏，不得在規格審查任務中自行建立。
- `data/assets.json` 是完整資產路徑與執行時資產 ID 的唯一來源；其他文件中的檔名只作簡稱。
- 背景素材依場景目錄和美術聖經命名，例如 `bg_ch01_tide_mark.webp`；角色、道具、前景、音效等依其所屬規格命名，不可臨時發明一套不一致的格式。
- 避免 `final.png`、`final2.png`、`newest.js`、`test-real-final.json` 等無法辨識用途的檔名。
- 不得把密碼、私人資訊或未授權素材放入檔名或路徑。

### 8.2 ID 永久性

- ID 使用小寫英文字母、數字及底線，並遵守 `docs/06_JSON_SCHEMA.md` 中各類型的前綴規則。
- ID 是資料引用用的穩定識別碼，不是顯示文字；可以修改顯示名稱，不可因改名而改掉已被引用的 ID。
- 場景 ID 例如 `ch01_tide_mark`、`ch01_grey_bell`、`ch01_record_room`。
- 角色、對話、事件、道具、任務、線索與資產 ID 必須依 06 的類型規則命名；不可自行讓不同類型共用同一 ID。
- 同一類型中不得重複 ID。刪除內容後也不要把舊 ID 分配給另一個新內容。
- 新增 ID 前先搜尋所有資料檔、程式和規格中的既有引用；不要只檢查目前編輯的檔案。

### 8.3 資源路徑

- 資源路徑以 repository 內的相對路徑為基準，遵守 `docs/06_JSON_SCHEMA.md` 和 `docs/08_TECH_SPEC.md`。
- GitHub Pages 可能將網站放在 repository 子路徑下；不要假設網站一定部署於網域根目錄。程式需遵循技術規格中的基底路徑處理方式。
- 不要把本機絕對路徑（例如電腦或手機的下載資料夾）寫進 JSON 或程式。
- 不要自行拼出尚不存在的圖片、音訊或 JSON 路徑。尚未製作的資源要列為待製作，並提供佔位方案。
- 更改路徑前先搜尋所有引用，更新資產索引及受影響的場景資料，並測試載入。
- 對非必要資源使用安全備援；背景或音訊缺失不應阻斷主線。
- 不要以外部熱連結作為核心素材的唯一來源，除非技術規格與授權審核明確允許。

## 9. 不得隨意重寫整個專案

預設採用**最小必要修改**。AI 不得因個人偏好、輸出方便或一次性修復，而無理由地整份替換程式、重建資料格式或搬動資料夾。

### 9.1 修改前

1. 讀取目標檔案完整內容及其直接依賴。
2. 確認目前 repository 狀態、檔案路徑、呼叫關係和相關測試。
3. 搜尋目標函式、ID、路徑及資料欄位在其他檔案中的引用。
4. 列出本次允許修改的範圍。
5. 若需要重構，先說明必要性、替代方案、影響範圍和回退方式；高風險重構先取得使用者確認。

### 9.2 修改中

- 優先做小而集中的變更。
- 不得刪掉不理解的程式碼、欄位、劇情、測試或備援邏輯。
- 不得用硬編碼值繞過正式資料契約或規格衝突。
- 不得以「重寫比較簡單」作為唯一理由。
- 不得把未使用的未來架構、框架或依賴順手加進來。
- 若發現必須超出範圍，先停止超出部分，回報差異並等待確認。

### 9.3 修改後

- 比對修改前後差異，檢查是否出現非任務要求的刪除或改名。
- 測試新功能及受影響的既有功能。
- 說明任何刻意保留的技術債、暫時方案或未完成內容。
- 若修改意外造成大範圍變更，先不要宣稱完成；應縮小差異或還原到最後已知良好狀態。

## 10. 修改前後的測試要求

### 10.1 修改前基準檢查

開始修改前，盡可能確認：

- 目標檔案存在且內容可讀。
- 目前程式／資料在未修改時的狀態。
- 與任務直接相關的既有流程是否可操作。
- 相關 JSON 原本是否可解析，引用是否存在。
- 目前已知錯誤、未完成項目及最近通過的 commit。
- 測試工具是否可用；若無法執行，先標示限制。

若專案當前尚無可執行遊戲或測試流程，應明確記錄「無既有可運行基準」，不可虛構修改前測試結果。

### 10.2 修改後最低測試

依變更類型選擇測試，並逐項報告結果：

| 變更類型 | 最低檢查 |
|---|---|
| HTML／CSS | 頁面可載入；窄螢幕無明顯溢出；按鈕與文字可讀；焦點與點擊區域合理 |
| JavaScript | 語法／載入錯誤檢查；新增流程可操作；錯誤分支有可理解提示 |
| JSON | 標準 JSON 解析；必要欄位與型別；ID 唯一；引用目標存在 |
| 場景資料 | 場景可載入；熱點可觸發；出口目的地有效；必要條件及重複觸發處理正確 |
| 劇情／事件 | 前置條件、選擇結果、旗標、線索、任務更新和資訊揭露順序一致 |
| 角色素材 | 檔案可開啟；角色外觀與規格一致；路徑與資產索引一致；授權狀態已記錄 |
| 存檔／讀檔 | 新存檔、重新載入、無效／舊存檔、匯出／匯入（若已實作）及錯誤提示 |
| 部署 | 子路徑下的相對路徑、資料和資產載入；部署網址實際打開；手機／平板人工測試（如可行） |

### 10.3 測試結果標記

只可使用以下清楚標記：

- **通過：** 已按列出的步驟實際執行，結果符合驗收條件。
- **失敗：** 已執行，結果不符合驗收條件；附上錯誤與重現步驟。
- **未測試：** 沒有執行，不代表通過。
- **受阻：** 因工具、權限、設備、資料或外部服務等原因無法測試；說明阻礙和下一步。
- **部分通過：** 部分條件通過、部分失敗或未測試；逐項列出。

「程式看起來合理」「AI 沒看到問題」「檔案已提交」均不能代替實際測試。若只有靜態檢查，應寫「靜態檢查通過；瀏覽器行為未測試」。

### 10.4 手機／平板人工驗收

如果 AI 無法直接操作使用者的裝置，必須提供簡短、逐步的人工檢查清單，包含預期看到的畫面和遇到問題時要回報的資訊。不得聲稱已在使用者的手機或平板測試。

## 17. 最終交接原則

- 任務完成與否由檔案、差異、測試和驗收證據決定，不由 AI 的語氣決定。
- 文件已寫入、Git 已提交、程式可執行、手機實測通過、網站已發布是不同階段，必須分別報告。
- 不知道就寫不知道；沒測試就寫未測試；無權限就寫受阻。
- 優先交付小而可驗收的成果，讓使用者能理解、檢查、保存和回退。
- 若不確定下一步，回到 `docs/09_CONTENT_ROADMAP.md`，檢查前置條件並選擇第一個尚未完成且依賴已滿足的任務。

## 18. 第一章規格一致性檢查清單（2026-10-22）

每次建立或修改第一章資料前，必須逐項核對：

1. `record_handling` 只接受 `sealed`、`summary_shared`、`location_only`；每個選項都有唯一選項 ID、事件 ID、短回應及同一狀態欄位。
2. `ch01_anomaly_record_found` 是唯一「異常記錄已取得」旗標；不得再以 `ch01_anomaly_read` 表示同一狀態。
3. 低功率讀取必須同時驗證 `ch01_reader_inspected`、`ch01_archive_slots_checked`、`ch01_maintenance_marks_checked`、`ch01_isolation_ready`。
4. 一次讀取只發放一個 `item_anomaly_fragment`，同時解鎖 CL-05 與 CL-06；重複互動不得重複發獎。
5. 第一章完成事件只能在記錄已取得且 `record_handling` 合法時設定 `chapter_01_complete=true`。
6. 所有場景出口、事件、角色、任務、對話、道具、線索和資產引用都必須存在；未來章節佔位 ID 必須標示為未定案。
7. Pages 使用 `main/(root)`，`docs/` 只放文件；相對資源路徑須考慮 repository 子路徑。
8. 第一章存檔測試包含新遊戲、有效讀取、刷新恢復、損壞資料、寫入失敗及清除確認；手動匯入／匯出只屬後續可選。
9. 第一章結尾提供第二份獨立年代證據的查證方向；瑟嵐只作訊息／聯絡伏筆，不假定已有通訊系統。
10. 報告分開標示靜態文件檢查、JSON 解析、瀏覽器測試、手機實測及 Pages 部署實測。沒有執行的項目不得標為通過。
